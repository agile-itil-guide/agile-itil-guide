# ระบบคุณค่าบริการ ITIL

**ระบบคุณค่าบริการของ ITIL อธิบายว่าทุกสิ่งที่องค์กรทำ ตั้งแต่หลักการนำทางไปจนถึงแนวปฏิบัติประจำวัน ประกอบกันอย่างไรเพื่อเปลี่ยนความต้องการและโอกาสให้เป็นคุณค่า และมีประโยชน์ในฐานะแผนที่สำหรับการสนทนามากกว่าเป็นโครงสร้างที่ต้องลอกตาม**

## เหตุใดเรื่องนี้จึงสำคัญ

ระบบคุณค่าบริการ (service value system หรือ SVS) ของ ITIL 4 มาแทนที่วงจรชีวิตบริการแบบเส้นตรงของ ITIL เวอร์ชันก่อนด้วยแบบจำลองของส่วนประกอบที่ทำงานร่วมกัน สำหรับทีมเอไจล์ การเปลี่ยนแปลงนี้สำคัญ วงจรชีวิตบ่งบอกว่ากลยุทธ์มาก่อน ตามด้วยการออกแบบ การเปลี่ยนผ่าน และการปฏิบัติการเป็นขั้นสุดท้าย ซึ่งไม่เข้ากับทีมที่สร้าง ดูแล และเปลี่ยนแปลงบริการในสัปดาห์เดียวกัน ระบบของส่วนที่เชื่อมโยงกันอธิบายได้ทั้งวงจรการวางแผนรายเดือนและเหตุการณ์ขัดข้องคืนวันศุกร์

SVS ยังให้คำตอบร่วมสำหรับคำถามที่ทีมมักลำบากใจ คือ ทั้งหมดนี้มีไว้เพื่ออะไร คำตอบตามถ้อยคำของ ITIL ที่สรุปกันอย่างกว้างขวางคือ ระบบรับความต้องการและโอกาสเป็นอินพุต และผลิตคุณค่าเป็นเอาต์พุต กรอบนี้เชื่อมงานประจำวันของศูนย์บริการหรือทีมแพลตฟอร์มเข้ากับสิ่งที่ลูกค้าได้จากบริการ และให้วิธีถามว่าแนวปฏิบัติหนึ่งๆ ก่อให้เกิดคุณค่าหรือเพียงรับใช้กระบวนการ

หัวข้อนี้อธิบาย SVS และส่วนประกอบตามที่สรุปในเอกสารสาธารณะที่อ่านเพื่อจัดทำคู่มือนี้ เอกสารส่วนใหญ่มาจากผู้ให้บริการฝึกอบรมและผู้ขายซอฟต์แวร์ ไม่ใช่เจ้าของกรอบแนวทาง รายละเอียดจึงอาจต่างจากสิ่งพิมพ์ทางการ ในจุดที่สำคัญ ให้ตรวจสิ่งพิมพ์ปัจจุบันของเจ้าของ (ดูหัวข้อ 2.2 — ITIL สำหรับสถานะของเวอร์ชัน)

## แนวคิดหลัก

### คุณค่า ความต้องการ และโอกาส

หน้า ITIL 4 Foundation ของ PeopleCert อธิบายระบบคุณค่าบริการว่าเป็น "กรอบแนวทางที่จะช่วยคุณสร้าง ส่งมอบ และบริหารบริการ" แหล่งทุติยภูมิอธิบายอย่างเป็นรูปธรรมกว่านั้น คือรับ **โอกาสและความต้องการ** เป็นอินพุต และผลิต **คุณค่า** เป็นเอาต์พุต โอกาสคือช่องทางที่จะเพิ่มคุณค่าหรือปรับปรุงบางสิ่ง ความต้องการคือความจำเป็นหรือความปรารถนาที่ลูกค้าและผู้ใช้มีต่อผลิตภัณฑ์และบริการ

กรอบนี้สำคัญเพราะวางคุณค่าไว้ที่ฝั่งผลลัพธ์ บริการที่จัดการตั๋วทั้งหมดได้แต่ไม่ช่วยผู้ใช้ ยังไม่ได้สร้างคุณค่า ไม่ว่ากระบวนการจะดีเพียงใด และยังเตือนว่าอินพุตไม่ได้มีแต่คำขอ โอกาส เช่น เทคโนโลยีใหม่ที่อาจลดงานซ้ำซาก เข้าสู่ระบบอย่างเท่าเทียมกัน

### ห้าส่วนประกอบ

ผู้ให้บริการฝึกอบรมและผู้ขายอธิบายส่วนประกอบของ SVS ไว้ห้าอย่าง ตารางแสดงส่วนประกอบเหล่านั้นพร้อมคำอธิบายแบบง่ายและการตีความแบบเอไจล์

| ส่วนประกอบ | คืออะไร | การตีความแบบเอไจล์ |
|---|---|---|
| **หลักการนำทาง (Guiding principles)** | ข้อแนะนำเจ็ดข้อที่นำทางองค์กรในทุกสถานการณ์ | ชุดค่านิยมสั้นๆ สำหรับทดสอบแนวปฏิบัติใดๆ (ดูหัวข้อ 2.4 — หลักการนำทางของ ITIL) |
| **ธรรมาภิบาล (Governance)** | วิธีที่องค์กรถูกกำกับและควบคุม | ทิศทางที่ชัดเจนและขอบเขตที่ทีมตัดสินใจได้ภายใน (ดูหัวข้อ 5.7 — ธรรมาภิบาล ความเสี่ยง และการปฏิบัติตามข้อกำหนด) |
| **ห่วงโซ่คุณค่าบริการ (Service value chain)** | แบบจำลองการดำเนินงานที่เป็นศูนย์กลางของ SVS มีหกกิจกรรม | ชุดกิจกรรมที่ยืดหยุ่นซึ่งทีมนำมาผสมเป็นสายธารคุณค่า (ดูหัวข้อ 2.6 — ห่วงโซ่คุณค่าบริการ) |
| **แนวปฏิบัติ (Practices)** | ชุดทรัพยากรขององค์กรที่ออกแบบเพื่อทำงานหรือบรรลุวัตถุประสงค์ ITIL 4 ระบุ 34 ข้อ | ความสามารถที่คุณดึงมาใช้ ไม่ใช่กระบวนการที่คุณรันตามลำดับ (ดูส่วนที่ 3) |
| **การปรับปรุงอย่างต่อเนื่อง (Continual improvement)** | ความพยายามอย่างต่อเนื่องเพื่อปรับปรุงผลิตภัณฑ์ บริการ และแนวปฏิบัติ | นิสัยที่ทำให้ส่วนที่เหลือของระบบซื่อตรง (ดูหัวข้อ 3.15 — การปรับปรุงอย่างต่อเนื่อง) |

แหล่งทุติยภูมิแหล่งหนึ่งอธิบายหลักการนำทางว่าเป็นข้อแนะนำที่นำทางองค์กรได้ "ไม่ว่าเป้าหมาย กลยุทธ์ ประเภทของงาน หรือโครงสร้างการบริหารจะเปลี่ยนไปอย่างไร" อีกแหล่งอธิบายธรรมาภิบาลว่าเป็นวิธีที่องค์กรถูกกำกับและควบคุม

### ห่วงโซ่คุณค่าบริการที่ศูนย์กลาง

ห่วงโซ่คุณค่าบริการถูกอธิบายว่าเป็นแบบจำลองการดำเนินงานของ SVS หกกิจกรรมของมันตามที่สรุปกันอย่างกว้างขวางคือ วางแผน ปรับปรุง ทำให้ผู้ใช้มีส่วนร่วม ออกแบบและเปลี่ยนผ่าน จัดหาและสร้าง และส่งมอบและสนับสนุน แหล่งต่างๆ เน้นว่ากิจกรรมเหล่านี้ไม่ใช่ลำดับขั้น ทีมนำมาผสมกันในลำดับต่างๆ เพื่อสร้าง **สายธารคุณค่า (value stream)** ที่ตอบสนองสถานการณ์เฉพาะ เช่น การจัดการเหตุการณ์ขัดข้องหรือการปล่อยฟีเจอร์ใหม่ ดูหัวข้อ 2.6 — ห่วงโซ่คุณค่าบริการ เพิ่มเติม

### แนวปฏิบัติ

แนวปฏิบัติคือความสามารถที่องค์กรดึงมาใช้ แหล่งต่างๆ ระบุ 34 แนวปฏิบัติ เช่น การบริหารเหตุการณ์ขัดข้องและการสนับสนุนการเปลี่ยนแปลง และจัดกลุ่มเป็นแนวปฏิบัติการบริหารทั่วไป การบริหารบริการ และการบริหารด้านเทคนิค บทความ Wikipedia เรื่อง ITIL ให้จำนวนเท่ากันและแบ่งเป็นแนวปฏิบัติการบริหารผลิตภัณฑ์และบริการ 22 ข้อ และแนวปฏิบัติการบริหารทั่วไป 12 ข้อ การจัดกลุ่มต่างกันไปตามแหล่ง จึงควรใช้สิ่งพิมพ์ปัจจุบันของเจ้าของเมื่อต้องการรายการที่แน่นอน

ในบริบทเอไจล์ แนวปฏิบัติไม่ใช่เอกสารกระบวนการ แต่เป็นทรัพยากรที่ประกอบด้วยผู้คน สารสนเทศ เทคโนโลยี และวิถีการทำงานที่ทีมใช้ได้ แนวปฏิบัติเดียวกันอาจปรากฏในหลายสายธารคุณค่า

### SVS เกี่ยวข้องกับสี่มิติอย่างไร

PeopleCert ระบุสี่มิติของการบริหารบริการ ได้แก่ องค์กรและผู้คน สารสนเทศและเทคโนโลยี พันธมิตรและผู้ส่งมอบ และสายธารคุณค่าและกระบวนการ สี่มิตินี้ใช้กับทุกส่วนของ SVS แนวปฏิบัติ กิจกรรมของห่วงโซ่คุณค่า หรือหลักการนำทางแต่ละอย่างตรวจสอบผ่านสี่มิติได้เพื่อดูว่าขาดอะไร อาจเป็นทักษะ เครื่องมือ ข้อตกลงกับผู้ส่งมอบ หรือการไหลของงานที่กำหนดไว้ (ดูหัวข้อ 2.5 — สี่มิติของการบริหารบริการ)

### สิ่งที่ SVS ไม่ใช่

SVS คือแบบจำลอง ไม่ใช่ระเบียบวิธี มันไม่ได้บอกว่าคุณต้องทำตามขั้นตอนใด ไม่ได้กำหนดแผนผังองค์กร เครื่องมือ หรือกระบวนการตั๋วแบบเฉพาะ แบบจำลองทั่วไปเช่นนี้ยากที่จะโต้แย้งและอาจยากที่จะนำไปใช้ จึงควรตัดสินจากว่ามันช่วยให้ทีมถามคำถามที่ดีขึ้นหรือไม่ บทความ Wikipedia เรื่อง ITIL ไม่ได้อธิบาย SVS หรือระบุข้อวิจารณ์ หัวข้อนี้จึงไม่ระบุข้อวิจารณ์ใดให้เป็นของบุคคลที่มีชื่อ

### SVS ใน ITIL 5

PeopleCert ประกาศ ITIL 5 ในปี 2026 และบางแหล่งใช้ "ระบบคุณค่าบริการของ ITIL 4 และ ITIL 5" ควบคู่กัน คู่มือนี้ยืนยันจากหน้าสาธารณะของเจ้าของไม่ได้ว่า SVS ถูกอธิบายใน ITIL 5 อย่างไร หากคุณทำงานกับเวอร์ชันใหม่ ให้อ่านสิ่งพิมพ์ใหม่และเปรียบเทียบกับหัวข้อนี้

## แนวปฏิบัติที่ดี

1. **ใช้ SVS เป็นแผนที่ ไม่ใช่พิมพ์เขียว** วาดห้าส่วนประกอบฉบับองค์กรของคุณลงบนหน้าเดียว พร้อมสิ่งที่มีอยู่และสิ่งที่ขาด ใช้เพื่อเริ่มการสนทนา และอย่าทำให้เป็นแบบที่ต้องนำไปสร้างตาม
2. **เริ่มจากความต้องการและโอกาส** ระบุสิ่งที่เข้ามาที่ทีมของคุณ ได้แก่ คำขอ เหตุการณ์ขัดข้อง แนวคิด และโอกาส ถามว่าอะไรเพิ่มคุณค่าและอะไรเป็นสัญญาณรบกวน ติดตามโอกาสเช่นเดียวกับความต้องการ
3. **บอกว่าคุณค่าหมายถึงอะไรสำหรับแต่ละบริการ** สำหรับแต่ละบริการ เขียนหนึ่งหรือสองประโยคเกี่ยวกับคุณค่าสำหรับผู้ที่ใช้และสำหรับองค์กร ใช้ข้อความเหล่านี้ตัดสินแนวปฏิบัติ
4. **มองหลักการเป็นเครื่องทดสอบ** ทดสอบการเปลี่ยนแปลงกระบวนการที่เสนอกับหลักการทั้งเจ็ดข้อ หากไม่ผ่านข้อใด ให้ถามว่าเพราะอะไร แล้วเปลี่ยนมัน หรือจดข้อแลกเปลี่ยนไว้ (ดูหัวข้อ 2.4 — หลักการนำทางของ ITIL)
5. **นิยามธรรมาภิบาลด้วยถ้อยคำธรรมดา** ระบุว่าใครกำหนดทิศทาง ทีมทำงานภายในขอบเขตใด และตรวจผลอย่างไร ธรรมาภิบาลที่ชัดเจนสำหรับทีมทำให้ทีมลงมือได้เร็ว (ดูหัวข้อ 5.7 — ธรรมาภิบาล ความเสี่ยง และการปฏิบัติตามข้อกำหนด)
6. **คิดถึงสายธารคุณค่า ไม่ใช่แผนก** ติดตามว่างานไหลจากความต้องการไปสู่คุณค่าอย่างไรสำหรับหนึ่งบริการ ข้ามทีม เสริมจุดที่อ่อนที่สุด ไม่ใช่แผนกที่บริหารดีที่สุด
7. **มองแนวปฏิบัติเป็นทรัพยากรร่วม** ให้หลายทีมใช้แนวปฏิบัติเดียวกัน เช่น การบริหารเหตุการณ์ขัดข้อง ในสายธารคุณค่าของตนเอง ดูแลแนวปฏิบัติให้ส่วนกลางพอที่จะสม่ำเสมอ และให้ท้องถิ่นพอที่จะมีประโยชน์
8. **ตรวจทั้งสี่มิติ** เมื่อสิ่งใดไม่ได้ผล ให้ถามว่าช่องว่างอยู่ที่ผู้คน สารสนเทศและเทคโนโลยี พันธมิตรและผู้ส่งมอบ หรือกระบวนการ การแก้มิติผิดเป็นความสูญเปล่าที่พบบ่อย
9. **ทำให้การปรับปรุงอย่างต่อเนื่องมองเห็นได้** เก็บรายการปรับปรุงพร้อมเจ้าของและวันที่ และทบทวนอย่างสม่ำเสมอ กระบวนการปรับปรุงที่ไม่มีใครเห็นเป็นแค่เจตนาดี
10. **ทำแบบจำลองให้เล็ก** หากแผนภาพหรือเอกสารเกี่ยวกับ SVS ยาวเกินหนึ่งหน้า ให้หยุดและถามว่าใครจะใช้ แบบจำลองที่ไม่มีใครใช้ไม่มีคุณค่า
11. **ใช้สิ่งพิมพ์ปัจจุบันของเจ้าของสำหรับนิยาม** เมื่อต้องการนิยามที่แน่นอนสำหรับการตรวจสอบหรือสัญญา ให้นำจากเจ้าของกรอบแนวทาง ไม่ใช่จากสรุป รวมถึงสรุปนี้ด้วย
12. **กลับมาดูแผนที่ทุกปี** ตรวจว่าส่วนประกอบยังอธิบายวิธีที่องค์กรทำงานอยู่หรือไม่ โดยเฉพาะหลังการปรับโครงสร้างหรือเมื่อมีกรอบแนวทางเวอร์ชันใหม่

## คำถามสำหรับพูดคุยกับทีมของคุณ

**บริการหลักของเราสร้างคุณค่าอะไรให้ผู้ที่ใช้ ด้วยถ้อยคำของพวกเขา**

ขอให้ทุกคนเขียนหนึ่งประโยคแล้วเปรียบเทียบ ความแตกต่างแสดงว่าทีมมีภาพไม่ตรงกัน ถามว่ามีหลักฐานอะไรรองรับคำอธิบาย เช่น ข้อเสนอแนะของผู้ใช้หรือข้อมูลการใช้งาน ทีมมักพบว่าตนรู้จักกระบวนการของตนมากกว่ารู้จักคุณค่า ผู้อำนวยการสนทนาอาจปิดด้วยการร่างประโยคร่วมหนึ่งประโยคและจดว่าหลักฐานใดยังขาด

**ความต้องการและโอกาสอะไรเข้ามาที่ทีมของเรา และเราแยกว่าสิ่งใดควรลงมือทำอย่างไร**

ระบุแหล่งที่มา ได้แก่ ตั๋ว โครงการ แนวคิด การเปลี่ยนแปลงด้านกฎระเบียบ เครื่องมือใหม่ ถามว่าใครตัดสินว่ารับอะไรและอย่างไร มองหาโอกาสที่ไม่เคยได้เวลาเพราะความต้องการเต็มวัน ถามว่าการเพิกเฉยแต่ละข้อจะสูญเสียอะไร เลือกหนึ่งโอกาสไปพิจารณาในเดือนหน้า

**ส่วนประกอบทั้งห้าอย่างใดที่เรามีอยู่ในรูปแบบใดรูปแบบหนึ่ง และอย่างใดอ่อนที่สุด**

วาดห้าส่วนประกอบบนกระดาน และทำเครื่องหมายแต่ละอย่างว่าชัดเจน ชัดเจนบางส่วน หรือขาด ขอตัวอย่างล่าสุดที่อยู่เบื้องหลังแต่ละเครื่องหมาย ส่วนประกอบที่อ่อนที่สุดมักอธิบายปัญหาที่เกิดซ้ำ ธรรมาภิบาลที่ไม่ชัดทำให้ตัดสินใจช้า และการขาดนิสัยปรับปรุงทำให้เหตุการณ์ขัดข้องเกิดซ้ำ เลือกหนึ่งอย่างไปเสริม

**งานชิ้นล่าสุดชิ้นหนึ่งไหลจากความต้องการไปสู่คุณค่าข้ามทีมของเราอย่างไร**

ติดตามตัวอย่างหนึ่งจากคำขอแรกจนถึงคุณค่าที่ส่งมอบ ระบุทีมและการส่งต่อ มองหาการรอคอยและขั้นตอนที่ไม่เพิ่มอะไร ถามว่าใครเห็นเส้นทางทั้งหมด เป้าหมายคือการอธิบายสายธารคุณค่าในทางปฏิบัติ (ดูหัวข้อ 5.4 — การบริหารสายธารคุณค่า) เลือกการส่งต่อหนึ่งจุดไปปรับปรุง

**ช่องว่างด้านผู้คน เทคโนโลยี ผู้ส่งมอบ หรือกระบวนการ ปรากฏบ่อยที่สุดตรงไหนในเหตุการณ์ขัดข้องของเรา**

ทบทวนเหตุการณ์ขัดข้องหรือความล่าช้าล่าสุดสองสามเรื่อง และทำเครื่องหมายว่าแต่ละเรื่องชี้ไปที่มิติใด รูปแบบอาจเปิดเผยบางอย่าง ปัญหาจำนวนมากในมิติพันธมิตรบ่งชี้ว่าข้อตกลงกับผู้ส่งมอบไม่ชัดเจน อย่ามองแบบฝึกหัดนี้เป็นการวินิจฉัย มันเป็นตัวกระตุ้น ถามว่าการเปลี่ยนแปลงหนึ่งอย่างในมิติที่อ่อนที่สุดจะส่งผลอย่างไร

**การปรับปรุงหนึ่งข้อที่เราสัญญาไว้แต่ไม่ได้ส่งมอบคืออะไร และเพราะเหตุใด**

ขอรายการที่เก่าที่สุดในรายการปรับปรุงใดก็ได้ หาว่าไม่เคยได้จัดลำดับความสำคัญ เสียเจ้าของไป หรือกลายเป็นไม่เกี่ยวข้อง คำตอบที่ตรงไปตรงมาแสดงว่าการปรับปรุงอย่างต่อเนื่องถูกจริงจังเพียงใด ตกลงตัดสินใจเรื่องรายการนั้น ได้แก่ ทำ กำหนดเวลา หรือทิ้งอย่างเปิดเผย

## ในทางปฏิบัติ: ตัวอย่าง ITIL แบบเอไจล์

บริการห้องสมุดสาธารณะแห่งชาติดำเนินแพลตฟอร์มยืมหนังสือดิจิทัลที่ผู้อ่านทั่วประเทศใช้ โดยมีทีมสิบสี่คนแบ่งเป็นกลุ่มพัฒนากับกลุ่มปฏิบัติการ ผู้นำถามว่าทำไมแพลตฟอร์มจึงล่มซ้ำๆ ระหว่างกิจกรรมยอดนิยม เช่น แคมเปญอ่านหนังสือช่วงฤดูร้อน ทั้งที่แต่ละทีมรายงานว่าปฏิบัติตามกระบวนการของตนได้ดี

ผู้นำด้านการปรับปรุงจัดเวิร์กช็อปโดยใช้ระบบคุณค่าบริการ กลุ่มเริ่มจากความต้องการและโอกาส แคมเปญเป็นที่รู้ล่วงหน้าหลายเดือน แต่ข้อมูลถึงกลุ่มปฏิบัติการเพียงหนึ่งสัปดาห์ก่อนเริ่ม พวกเขาอธิบายคุณค่าของแพลตฟอร์มด้วยถ้อยคำของผู้อ่าน คือการยืมหนังสือได้ในเวลาไม่ถึงหนึ่งนาที และเห็นว่าไม่มีตัวชี้วัดใดครอบคลุมเรื่องนั้น ในส่วนประกอบแนวปฏิบัติ พวกเขาพบว่าไม่มีใครทำการวางแผนความจุ เพราะตกอยู่ระหว่างฝ่ายพัฒนากับฝ่ายปฏิบัติการ ธรรมาภิบาลไม่ชัดว่าใครอนุมัติการเพิ่มค่าใช้จ่ายคลาวด์ชั่วคราวได้

กลุ่มตกลงเปลี่ยนสามเรื่อง ทีมสื่อสารแบ่งปันปฏิทินแคมเปญเมื่อกำหนดแล้ว วิศวกรที่ระบุชื่อคนหนึ่งเป็นเจ้าของการวางแผนความจุของแพลตฟอร์มและรายงานก่อนแต่ละแคมเปญ หัวหน้าฝ่ายบริการดิจิทัลกำหนดวงเงินใช้จ่ายที่ทีมใช้ได้โดยไม่ต้องขออนุมัติระหว่างแคมเปญ แคมเปญถัดไปผ่านไปโดยไม่มีการล่ม ยังมีปัญหาเหลืออยู่ ผู้ส่งมอบบริการค้นหาไม่ถูกรวมในการวางแผนและช้าลงเมื่อรับภาระหนัก และตัวชี้วัดของผู้อ่านยังเป็นการประมาณ ไม่ได้วัดจริง ทีมเพิ่มผู้ส่งมอบเข้าที่ประชุมวางแผน และเริ่มบันทึกเวลาตอบสนองของหน้าเว็บเป็นตัวชี้วัดแรก

## สี่มุมมอง

### ทีมผลิตภัณฑ์และทีมส่งมอบ

ทีมส่งมอบใช้ SVS เพื่อมองเห็นเส้นทางทั้งหมดจากความต้องการไปสู่คุณค่า ดูว่างานของคุณถึงผู้ใช้อย่างไรและใครสนับสนุน เสนอโอกาส เช่น การทำงานอัตโนมัติ นอกเหนือจากคำขอ เข้าร่วมการสนทนาด้านธรรมาภิบาลเพื่อให้ขอบเขตเหมาะกับวิธีที่คุณทำงาน

### ทีมบริการและทีมปฏิบัติการ

ทีมปฏิบัติการแบกแนวปฏิบัติหลายข้อใน SVS ใช้แบบจำลองแสดงว่าแนวปฏิบัติของคุณรับใช้สายธารคุณค่า ไม่ใช่เพียงเป้าหมายภายใน อธิบายสิ่งที่คุณต้องการจากทีมส่งมอบและผู้ส่งมอบ และใช้สี่มิติอธิบายช่องว่าง

### ภาวะผู้นำและธรรมาภิบาล

ผู้นำรับผิดชอบธรรมาภิบาลและทิศทาง ทำให้การตัดสินใจเรื่องลำดับความสำคัญและขอบเขตชัดเจนและเข้าถึงได้ ถามว่าระบบผลิตคุณค่าที่คุณมองเห็นหรือไม่ และมีหลักฐานอะไรรองรับ หลีกเลี่ยงการขอให้ทีมจำลองแผนภาพ SVS ในเอกสารของตน

### ลูกค้าและผู้ใช้

ลูกค้าและผู้ใช้เป็นผู้ให้ความต้องการและรับคุณค่า พึงคาดหวังว่าจะถูกถามว่าคุณค่าหมายถึงอะไรสำหรับคุณ และเห็นสิ่งนั้นสะท้อนในวิธีที่บริการถูกวางแผนและวัด บอกผู้ให้บริการเรื่องโอกาสนอกเหนือจากข้อร้องเรียน เพราะทั้งสองป้อนเข้าสู่ระบบ

## รูปแบบความล้มเหลวที่พบบ่อย

- **วาดแผนภาพแล้วหยุด** แบบจำลองกลายเป็นโปสเตอร์ แก้ไขโดยใช้มันระบุส่วนประกอบที่อ่อนหนึ่งอย่างและปรับปรุงมัน
- **มองแนวปฏิบัติเป็นกระบวนการตามลำดับ** ทีมรันขั้นตอนตามลำดับเคร่งครัดสำหรับทุกอย่าง แก้ไขโดยผสมแนวปฏิบัติเป็นสายธารคุณค่าที่เหมาะกับสถานการณ์
- **เพิกเฉยต่อโอกาส** ติดตามเฉพาะความต้องการ และแนวคิดปรับปรุงไม่เคยได้เวลา แก้ไขโดยเก็บรายการโอกาสที่มองเห็นได้และทบทวนมัน
- **ธรรมาภิบาลคลุมเครือ** ไม่มีใครรู้ว่าใครตัดสินใจ แก้ไขโดยเขียนทิศทาง ขอบเขต และสิทธิการตัดสินใจด้วยภาษาธรรมดา
- **ทำให้ส่วนประกอบเดียวดีที่สุด** คลังแนวปฏิบัติที่งดงามไม่ช่วยหากสายธารคุณค่าพัง แก้ไขโดยตรวจทุกส่วนประกอบและทั้งสี่มิติ
- **สับสนสรุปกับตัวกรอบแนวทาง** สไลด์ฝึกอบรมถูกถือเป็นนิยาม แก้ไขโดยใช้สิ่งพิมพ์ของเจ้าของเมื่อต้องการความแม่นยำ
- **ไม่มีตัวชี้วัดคุณค่า** ทีมรายงานกิจกรรมและแสดงประโยชน์ไม่ได้ แก้ไขโดยเลือกอย่างน้อยหนึ่งตัวชี้วัดที่สะท้อนสิ่งที่ผู้ใช้ได้รับ
- **คัดลอกแบบจำลองลงทุกเอกสาร** การใช้มากเกินก่อให้เกิดความเหยียดหยัน แก้ไขโดยใช้สั้นๆ ในจุดที่ช่วยได้ และให้งานประจำวันแสดงผลลัพธ์

- [ ] มีรายการปรับปรุงที่มองเห็นได้พร้อมเจ้าของและวันที่
- [ ] เราใช้สิ่งพิมพ์ของเจ้าของกรอบแนวทางสำหรับนิยามที่แน่นอน
- [ ] แผนที่ถูกทบทวนอย่างน้อยปีละครั้ง

## พรอมต์ปัญญาประดิษฐ์

**วัตถุประสงค์: วาดแผนที่ของคุณเองสำหรับห้าส่วนประกอบ**

```text
Help me describe how the five components of the ITIL service value system appear in my organization. The components are: guiding principles, governance, service value chain, practices, and continual improvement.

About us: [describe the organization, team, and main services in a few sentences].
What we do for each component today, as best I can say: [write a sentence or two for each; write "unknown" where you cannot].

For each component, say whether my description shows it as clear, partly clear, or missing, and quote my words. Suggest one question for the team per component. Do not add facts about ITIL that I did not paste. Ask me clarifying questions first, and list what you are unsure of.
```

**วัตถุประสงค์: จำแนกความต้องการและโอกาส**

```text
Here is a list of things that came to our team in the last [period]: [paste short descriptions, one per line].

Classify each as demand (a request or need), incident, or opportunity (a chance to add value or improve something). For each, say in one sentence what value it might create for users or the organization, using only what I wrote. Mark items where you cannot tell. Then suggest two questions about what we are not getting time for. Do not invent details, and list what you are unsure of.
```

**วัตถุประสงค์: เขียนข้อความคุณค่าสำหรับบริการ**

```text
Help me write a value statement for the service [name].

What the service does: [describe].
Who uses it and what they say about it: [paste feedback or write "none"].
Any data we have: [paste facts, or write "none"].

Write two versions of a one-sentence statement of the value for users, and one of the value for the organization. Use only the information given. Mark any phrase that is a guess. Suggest one measure we could start collecting that would show whether the value is delivered, without inventing numbers. Ask clarifying questions first, and list what you are unsure of.
```

**วัตถุประสงค์: ติดตามสายธารคุณค่าข้ามทีม**

```text
Help me trace the flow of one piece of work from demand to delivered value.

The work: [describe, such as "a request for a new access role"].
Steps in order, with the team that did each, and dates if known: [paste].

Produce a simple text diagram of the stream. Mark each handoff and each wait, using only dates I gave. Identify the two longest waits and suggest questions to ask about them. If dates are missing, say what to collect. Mark assumptions, and list what you are unsure of.
```

## ทักษะปัญญาประดิษฐ์

- [raci-matrix](../../../../skills/raci-matrix/SKILL.md): ใช้ทำให้ธรรมาภิบาลและสิทธิการตัดสินใจของบริการชัดเจน
- [kaizen](../../../../skills/kaizen/SKILL.md): ใช้เปลี่ยนส่วนประกอบการปรับปรุงอย่างต่อเนื่องให้เป็นการเปลี่ยนแปลงเล็กๆ สม่ำเสมอ
- [stakeholder-analysis](../../../../skills/stakeholder-analysis/SKILL.md): ใช้ทำความเข้าใจว่าใครให้ความต้องการและใครรับคุณค่า
- [enterprise-architecture](../../../../skills/enterprise-architecture/SKILL.md): ใช้เมื่อทำแผนที่ว่าบริการ แนวปฏิบัติ และเทคโนโลยีเข้ากันอย่างไรในระดับองค์กร
