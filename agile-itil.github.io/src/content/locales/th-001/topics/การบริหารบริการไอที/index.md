# การบริหารบริการไอที

**การบริหารบริการไอที (IT service management หรือ ITSM) คือศาสตร์ว่าด้วยการออกแบบ ส่งมอบ ปฏิบัติการ และปรับปรุงบริการไอทีให้ตรงกับสิ่งที่ลูกค้าต้องการ และทีมเอไจล์ที่ดูแลบริการอยู่แล้วก็ทำสิ่งนี้อยู่ ไม่ว่าจะเรียกชื่อนี้หรือไม่ก็ตาม**

## เหตุใดเรื่องนี้จึงสำคัญ

เมื่อทีมส่งมอบซอฟต์แวร์แล้วดูแลให้ซอฟต์แวร์นั้นทำงานต่อ ทีมก็กลายเป็นผู้ให้บริการ ผู้ใช้พึ่งพาทีม คาดหวังว่าบริการจะพร้อมใช้งาน และต้องการความช่วยเหลือเมื่อบริการขัดข้อง ITSM คือชุดแนวปฏิบัติที่เติบโตขึ้นรอบความสัมพันธ์แบบนี้ ทีมที่เมินเฉยต่อ ITSM มักต้องกลับมาค้นพบมันด้วยวิธีที่เจ็บปวด ไม่ว่าจะเป็นการถูกเรียกตัวตอนกลางคืน การไม่รู้ว่ามีอะไรเปลี่ยนไปบ้าง หรือการเถียงกับลูกค้าว่าเคยสัญญาอะไรไว้

ITSM มีชื่อเสียงว่าเป็นกระบวนการที่หนักหน่วง และชื่อเสียงนี้ส่วนหนึ่งก็สมควรได้รับ ส่วนทีมเอไจล์ก็มีชื่อเสียงว่าเคลื่อนไหวรวดเร็วแล้วปล่อยให้ฝ่ายปฏิบัติการรับมือกับผลที่ตามมา ชื่อเสียงทั้งสองด้านเป็นภาพของความล้มเหลว ไม่ใช่เจตนาของศาสตร์ใดศาสตร์หนึ่ง ITSM ถามว่าลูกค้าต้องการอะไรจากบริการ และผู้ให้บริการจะส่งมอบและปรับปรุงบริการนั้นอย่างไร ซึ่งเป็นคำถามที่ทีมเอไจล์ใส่ใจเช่นกัน

หัวข้อนี้ให้คำศัพท์ที่ใช้ในส่วนอื่นของคู่มือ ได้แก่ บริการคืออะไร ใครคือลูกค้าและผู้ใช้ ITSM ครอบคลุมอะไรบ้าง และกรอบแนวทางหลักมาจากไหน หัวข้อนี้ใช้ [บทความ Wikipedia เรื่อง IT service management](https://en.wikipedia.org/wiki/IT_service_management) เป็นแผนที่ บทความดังกล่าวสั้นและแจกแจงรายชื่อกรอบแนวทางมากกว่าอธิบาย หัวข้อนี้จึงเพิ่มการตีความเชิงปฏิบัติและระบุไว้ทุกครั้งที่ทำเช่นนั้น

## แนวคิดหลัก

### ITSM คืออะไร

บทความ Wikipedia นิยาม ITSM ว่าเป็นชุดกิจกรรมที่องค์กรทำเพื่อออกแบบ สร้าง ส่งมอบ ปฏิบัติการ และควบคุมบริการไอทีที่เสนอให้ลูกค้า บทความเปรียบเทียบ ITSM กับแนวทางที่มุ่งเทคโนโลยี เช่น การบริหารเครือข่ายและการบริหารระบบ โดยระบุว่า ITSM ใช้แนวทางเชิงกระบวนการ มุ่งที่ความต้องการของลูกค้ามากกว่าตัวระบบ และเน้นการปรับปรุงอย่างต่อเนื่อง

บทความอ้างถึงผลสำรวจปี 2017 ของ CIO WaterCooler ที่รายงานว่าธุรกิจใช้ ITSM ส่วนใหญ่เพื่อสนับสนุนประสบการณ์ของลูกค้า (ร้อยละ 35) และคุณภาพของบริการ (ร้อยละ 48) นี่เป็นผลสำรวจเพียงชิ้นเดียว และบทความไม่ได้อธิบายกลุ่มตัวอย่าง ดังนั้นควรมองตัวเลขเหล่านี้เป็นตัวอย่างว่าผู้ปฏิบัติงานอธิบายเป้าหมายของตนอย่างไร ไม่ใช่เครื่องวัดว่าเป้าหมายแต่ละอย่างพบได้บ่อยเพียงใด

### บริการ ลูกค้า และผู้ใช้

**บริการ** คือวิธีส่งมอบคุณค่าให้ผู้อื่นโดยที่พวกเขาไม่ต้องเป็นเจ้าของต้นทุนและความเสี่ยง การชำระเงินออนไลน์ของธนาคาร การจองนัดหมายของโรงพยาบาล และพื้นที่จัดเก็บไฟล์ร่วมของบริษัทล้วนเป็นบริการ บทความแยก **ผู้ใช้** ซึ่งใช้บริการ ออกจาก **ลูกค้า** ซึ่งเป็นผู้จ่ายเงินหรือว่าจ้างให้จัดทำบริการ ในงานไอทีภายในบริษัท ลูกค้าอาจเป็นหัวหน้าหน่วยธุรกิจ และผู้ใช้คือพนักงานของหน่วยนั้น ในบริการสาธารณะ ลูกค้าอาจเป็นกระทรวง และผู้ใช้คือประชาชน ทั้งสองกลุ่มมีความต้องการต่างกัน และผู้ให้บริการที่รับฟังเฉพาะลูกค้าอาจมองข้ามสิ่งที่ผู้ใช้ประสบ

### กิจกรรมทั่วไปของ ITSM

บทความระบุแนวคิดหลักไว้ไม่กี่อย่าง และแนวปฏิบัติ ITSM มาตรฐานเพิ่มอีกหลายอย่าง เมื่อรวมกันแล้วได้ภาพรวมที่จดจำได้ดังนี้

| กิจกรรม | มีไว้เพื่ออะไร | คู่มือนี้กล่าวถึงที่ใด |
|---|---|---|
| **ศูนย์บริการ (Service desk)** | จุดติดต่อเดียวระหว่างผู้ให้บริการกับผู้ใช้ รับเหตุการณ์ขัดข้องและคำขอใช้บริการ | หัวข้อ 3.1 — ศูนย์บริการ |
| **การจัดการเหตุการณ์ขัดข้อง** | การกู้คืนบริการเมื่อมีสิ่งใดรบกวนหรือคุกคามบริการ | หัวข้อ 3.2 — การบริหารเหตุการณ์ขัดข้อง |
| **คำขอใช้บริการ** | การจัดหาสิ่งที่ผู้ใช้ขอเป็นประจำ เช่น สิทธิ์เข้าถึงหรืออุปกรณ์ | หัวข้อ 3.6 — การบริหารคำขอใช้บริการ |
| **ปัญหาและการเปลี่ยนแปลง** | การค้นหาและแก้สาเหตุเบื้องหลัง และการควบคุมการปรับเปลี่ยนบริการ | หัวข้อ 3.3 — การบริหารปัญหา และหัวข้อ 3.4 — การสนับสนุนการเปลี่ยนแปลง |
| **ระดับบริการและแค็ตตาล็อก** | การตกลงว่าเสนออะไรและดีเพียงใด | หัวข้อ 3.7 — การบริหารระดับบริการ และหัวข้อ 3.8 — การบริหารแค็ตตาล็อกบริการ |
| **การปรับปรุงอย่างต่อเนื่อง** | การทำให้บริการดีขึ้นเมื่อเวลาผ่านไป | หัวข้อ 3.15 — การปรับปรุงอย่างต่อเนื่อง |

บทความนิยาม **เหตุการณ์ขัดข้อง (incident)** ว่าเป็นการหยุดชะงักหรือแนวโน้มที่จะหยุดชะงักของความพร้อมใช้งานหรือคุณภาพของบริการ และนิยาม **คำขอใช้บริการ (service request)** ว่าเป็นคำขอตามปกติเพื่อรับบริการ บทความเอ่ยถึง **ข้อตกลงระดับบริการ (SLA)** เพียงผ่านๆ คู่มือจึงอธิบายไว้ในหัวข้อ 3.7 — การบริหารระดับบริการ

### การบริหารบริการระดับองค์กรและการทำงานอัตโนมัติ

บทความกล่าวถึงส่วนขยายสองอย่าง **การบริหารบริการระดับองค์กร (enterprise service management หรือ ESM)** นำเครื่องมือและแนวคิด ITSM ไปใช้กับส่วนอื่นของธุรกิจ เช่น ทรัพยากรบุคคลหรืออาคารสถานที่ ซึ่งก็รับคำขอและส่งมอบบริการเช่นกัน **การทำกระบวนการไอทีอัตโนมัติ (IT process automation)** แทนที่ขั้นตอนที่ต้องทำด้วยมือเป็นประจำด้วยขั้นตอนอัตโนมัติ เพื่อให้เจ้าหน้าที่มุ่งไปที่งานที่สำคัญกว่า ทั้งสองอย่างมีความสำคัญต่อทีมเอไจล์ เพราะ ESM แสดงว่าศาสตร์นี้ไม่ได้ผูกกับไอทีเท่านั้น และการทำงานอัตโนมัติคือวิธีที่ทีมเล็กรับมือกับปริมาณงานได้

### กรอบแนวทางและมาตรฐาน

บทความแจกแจงกรอบแนวทางและมาตรฐานไว้มากมาย ตารางด้านล่างทวนคำอธิบายบรรทัดเดียวของบทความ และขยายความต่อในหัวข้อ 2.7 — กรอบแนวทางและมาตรฐานการบริหารบริการไอที

| ชื่อ | สิ่งที่บทความระบุ |
|---|---|
| [ITIL](https://en.wikipedia.org/wiki/ITIL) | แนวปฏิบัติโดยละเอียดสำหรับ ITSM และการบริหารสินทรัพย์ไอที เพื่อให้ไอทีสอดคล้องกับเป้าหมายทางธุรกิจ |
| [ISO/IEC 20000](https://en.wikipedia.org/wiki/ISO/IEC_20000) | มาตรฐานสากลสำหรับระบบการบริหารบริการ ซึ่งองค์กรขอรับการรับรองได้ |
| [COBIT](https://en.wikipedia.org/wiki/COBIT) | กรอบแนวทางธรรมาภิบาลไอทีที่มีวัตถุประสงค์การควบคุม ตัวชี้วัด และแบบจำลองความเป็นผู้ใหญ่ |
| [FitSM](https://en.wikipedia.org/wiki/FitSM) | มาตรฐานแบบเบา ที่สอดคล้องกับ ISO/IEC 20000 เป็นส่วนใหญ่ |
| [CMMI](https://en.wikipedia.org/wiki/CMMI) | แบบจำลองสำหรับการสร้าง บริหาร และปรับปรุงบริการ |
| [TOGAF](https://en.wikipedia.org/wiki/TOGAF) | กรอบแนวทางที่เชื่อมเป้าหมายทางธุรกิจกับวัตถุประสงค์ด้านสถาปัตยกรรม |
| [Microsoft Operations Framework](https://en.wikipedia.org/wiki/Microsoft_Operations_Framework) | แนวทางการบริหารบริการที่อิงเทคโนโลยีของ Microsoft |
| [Application Services Library](https://en.wikipedia.org/wiki/Application_Services_Library) | กรอบแนวทางสำหรับการบริหารแอปพลิเคชันอย่างมืออาชีพ |
| [Business Information Services Library](https://en.wikipedia.org/wiki/Business_Information_Services_Library) | กรอบแนวปฏิบัติที่ดีสำหรับการบริหารสารสนเทศ |
| Business Process Framework (eTOM) | กรอบกระบวนการสำหรับผู้ให้บริการโทรคมนาคม |

บทความเสริมว่ากรอบแนวทาง ITSM ได้รับอิทธิพลจาก ISO 9000, ISO/IEC 27000 และ CMMI และว่า ITIL เวอร์ชัน 2 กับ BS 15000 ซึ่งเป็นมาตรฐานก่อนหน้า ISO/IEC 20000 สอดคล้องกันและกัน บทความยังอธิบาย USM ซึ่งเป็นระบบการบริหารแบบอิงหลักการที่รัฐบาลเนเธอร์แลนด์นำมาใช้

### สิ่งที่บทความไม่ครอบคลุม

บทความไม่มีส่วนประวัติศาสตร์ ไม่มีข้อวิจารณ์ และไม่เอ่ยถึงเอไจล์หรือ DevOps ความเงียบนี้สำคัญ ITSM ถูกวิจารณ์ว่าเพิ่มภาระกระบวนการและเปลี่ยนแปลงช้า และทีมเอไจล์ถูกวิจารณ์ว่าละเลยงานปฏิบัติการ แต่คุณจะไม่พบข้อวิจารณ์ใดเลยที่นั่น คู่มือนี้เติมช่องว่างดังกล่าวในส่วนที่ 5 โดยเริ่มจากหัวข้อ 5.1 — การบริหารบริการแบบเอไจล์ เมื่อหัวข้อนี้กล่าวถึงปัญหา ก็อาศัยแหล่งอื่นของคู่มือและประสบการณ์เชิงปฏิบัติ และระบุไว้เช่นนั้น

### ITSM และ ITAM

บทความเรื่อง ITIL อธิบายว่า ITIL ครอบคลุมทั้ง ITSM และการบริหารสินทรัพย์ไอที (IT asset management หรือ ITAM) ITAM คือศาสตร์ว่าด้วยการรู้ว่าองค์กรมีสินทรัพย์ไอทีอะไร มีต้นทุนเท่าใด และใช้อย่างไร บริการพึ่งพาสินทรัพย์ และทั้งสองศาสตร์ใช้ข้อมูลร่วมกัน ส่วนที่ 4 จึงตามหลัง ITSM อย่างใกล้ชิด (ดูหัวข้อ 4.1 — การบริหารสินทรัพย์ไอที)

## แนวปฏิบัติที่ดี

1. **นิยามบริการจากมุมของลูกค้า** ระบุสิ่งที่ลูกค้าและผู้ใช้ใช้จริงด้วยถ้อยคำของพวกเขา เช่น "เข้าสู่ระบบ" "จองนัดหมาย" และ "ส่งใบแจ้งหนี้" แล้วจัดกลุ่มเทคโนโลยีเบื้องหลังของแต่ละบริการ นี่คือจุดเริ่มต้นของแค็ตตาล็อกบริการ (ITIL สะกดว่า "service catalogue" ดูหัวข้อ 3.8 — การบริหารแค็ตตาล็อกบริการ)
2. **ระบุว่าใครคือลูกค้าและใครคือผู้ใช้** สำหรับแต่ละบริการ ให้จดว่าใครเป็นผู้จ่ายเงินหรือว่าจ้าง และใครเป็นผู้ใช้ หากเป็นคนละกลุ่ม ให้ตรวจว่าทั้งสองกลุ่มมีเสียงในเรื่องนี้
3. **ให้ทุกบริการมีเจ้าของ** ระบุผู้รับผิดชอบหนึ่งคนต่อผลการดำเนินงานของบริการและการปรับปรุงบริการเมื่อเวลาผ่านไป หากไม่มีเจ้าของ ปัญหาของบริการจะไม่ใช่หน้าที่ของใคร
4. **เริ่มจากกิจกรรมที่เจ็บปวดที่สุด** หากปัญหาคือบริการล่มบ่อย ให้เสริมการจัดการเหตุการณ์ขัดข้องก่อน หากไม่มีใครรู้ว่าอะไรเปลี่ยนไป ให้เริ่มจากบันทึกการเปลี่ยนแปลง อย่านำแนวปฏิบัติ ITSM ทุกอย่างมาใช้พร้อมกัน
5. **ใช้ประตูบานเดียว** จัดที่เดียวให้ผู้ใช้ขอความช่วยเหลือและยื่นคำขอ และทำให้ใช้ง่าย ศูนย์บริการที่เข้าถึงยากจะถูกเลี่ยง และคุณจะสูญเสียข้อมูลที่ ITSM พึ่งพา
6. **แยกเหตุการณ์ขัดข้อง คำขอ และปัญหาออกจากกัน** เหตุการณ์ขัดข้องคือการหยุดชะงัก คำขอคือการร้องขอตามปกติ และปัญหาคือสาเหตุเบื้องหลัง คิวที่ปนกันซ่อนรูปแบบและบิดเบือนตัวชี้วัด
7. **บันทึกสิ่งที่สำคัญและไม่เกินนั้น** เก็บบันทึกเหตุการณ์ขัดข้อง การเปลี่ยนแปลง และสินทรัพย์ที่คุณจะใช้ตัดสินใจ ลบช่องข้อมูลที่ไม่มีใครอ่าน บันทึกคือต้นทุน และคุณควรบอกได้ว่าแต่ละบันทึกมีไว้เพื่ออะไร
8. **เลือกกรอบแนวทางตามปัญหา ไม่ใช่ตามกระแส** ใช้ ITIL, ISO/IEC 20000, COBIT หรือแบบจำลองที่เบากว่าเป็นแหล่งแนวคิดสำหรับปัญหาที่คุณมี นำส่วนที่ช่วยได้มาใช้และบอกว่าส่วนใดที่ละไว้
9. **ทำงานประจำให้เป็นอัตโนมัติ** มองหาขั้นตอนที่ซ้ำๆ เช่น การรีเซ็ตรหัสผ่านและการให้สิทธิ์เข้าถึง แล้วทำให้เป็นอัตโนมัติอย่างระมัดระวัง ทบทวนการทำงานอัตโนมัติเป็นระยะเพื่อไม่ให้ห่างจากสิ่งที่ผู้ใช้ต้องการ
10. **วัดสิ่งที่ลูกค้ารู้สึก** ติดตามความพร้อมใช้งาน เวลาที่ใช้กู้คืนบริการ และความพึงพอใจของผู้ใช้ ก่อนจะนับกิจกรรมภายใน ใช้ผลสำรวจจากบทความ Wikipedia เป็นเครื่องเตือนว่าผู้ปฏิบัติงานระบุอยู่แล้วว่าประสบการณ์ของลูกค้าและคุณภาพคือเป้าหมายหลัก
11. **มองออกไปนอกไอที** หากส่วนอื่นขององค์กรจัดการคำขอได้ไม่ดี ให้พิจารณาใช้เครื่องมือและแนวปฏิบัติร่วมกันผ่านการบริหารบริการระดับองค์กร อย่าบังคับให้พวกเขาใช้คำศัพท์ของไอที
12. **ปรับปรุงอย่างต่อเนื่อง** กันเวลาเป็นประจำเพื่อทบทวนว่าอะไรได้ผล โดยใช้ข้อมูลเหตุการณ์ขัดข้องและคำขอ และเพื่อทำการเปลี่ยนแปลงเล็กๆ (ดูหัวข้อ 3.15 — การปรับปรุงอย่างต่อเนื่อง)

## คำถามสำหรับพูดคุยกับทีมของคุณ

**เราให้บริการอะไรบ้าง ด้วยถ้อยคำที่ผู้ใช้ของเราจะใช้**

ขอให้ทุกคนเขียนสามสิ่งที่ผู้ใช้พึ่งพาเรามากที่สุด แล้วเปรียบเทียบรายการ ความแตกต่างมักแสดงว่าทีมมีภาพของบริการไม่ตรงกัน หรือทีมอธิบายบริการด้วยเทคโนโลยีแทนที่จะอธิบายด้วยการใช้งาน ผู้อำนวยการสนทนาอาจถามว่าบริการใดไม่มีเจ้าของที่ชัดเจน จากนั้นตกลงรายการบริการชุดแรกร่วมกัน

**ใครคือลูกค้าและใครคือผู้ใช้ของบริการหลักของเรา และพวกเขาต้องการสิ่งเดียวกันหรือไม่**

ระบุผู้ที่ว่าจ้างหรือจ่ายเงิน และผู้ที่ใช้งาน ถามว่าแต่ละฝ่ายต้องการอะไรจากบริการ ในงานไอทีภายใน ลูกค้าอาจสนใจต้นทุนและความเสี่ยง ส่วนผู้ใช้สนใจความเร็วและความง่าย ถามว่าจุดใดขัดแย้งกันและทีมรับรู้เรื่องนี้ได้อย่างไร เลือกความขัดแย้งหนึ่งเรื่องไปคุยกับคนจริงๆ

**ผู้ใช้ไปที่ไหนเมื่อต้องการความช่วยเหลือ และมีกี่ช่องทาง**

นับช่องทางทั้งหมด ได้แก่ พอร์ทัล เบอร์โทรศัพท์ อีเมล แชต หรือโต๊ะของเพื่อนร่วมงาน ถามว่าผู้ใช้ชอบช่องทางใดและเพราะเหตุใด ช่องทางไม่เป็นทางการหลายช่องทางหมายความว่าความต้องการบางส่วนมองไม่เห็น การสนทนาควรจบด้วยการตัดสินใจว่าจะคงช่องทางใด รวมช่องทางใด และจะรวบรวมสิ่งที่เข้ามาทางช่องทางไม่เป็นทางการอย่างไร

**เราแยกเหตุการณ์ขัดข้อง คำขอ และปัญหาออกจากกันได้ดีเพียงใด และจะเกิดอะไรขึ้นเมื่อเราปนกัน**

หยิบตั๋วล่าสุดสิบใบมาจัดประเภท ความเห็นที่ไม่ตรงกันแสดงว่าทีมมีนิยามต่างกัน ถามว่าหมวดที่ปนกันส่งผลอย่างไรต่อรายงานและลำดับความสำคัญ ตัวอย่างเช่น คำขอจำนวนมากในคิวเหตุการณ์ขัดข้องอาจทำให้การจัดการเหตุการณ์ขัดข้องดูช้า ตกลงนิยามและตัวอย่างที่เรียบง่ายร่วมกัน

**แนวปฏิบัติ ITSM ใดที่เรายังขาด หรือทำอยู่แค่บนกระดาษ**

ระบุแนวปฏิบัติในตารางข้างต้น แล้วให้คะแนนแต่ละข้อว่าใช้ได้ผล ใช้ได้บางส่วน หรือมีแค่บนกระดาษ ขอตัวอย่างล่าสุดของข้อที่ให้คะแนนว่าใช้ได้ผล ผู้อำนวยการสนทนาควรต้านความอยากอุดทุกช่องว่าง และควรถามว่าช่องว่างใดสร้างความเสียหายแก่ลูกค้ามากที่สุด

**เราอยากให้กรอบแนวทางทำอะไรให้เรา และเรากลัวว่ามันจะทำอะไรกับเรา**

รวบรวมความหวังและความกังวลเกี่ยวกับการนำ ITIL หรือ ISO/IEC 20000 มาใช้ ความหวังมักเป็นความสม่ำเสมอและความน่าเชื่อถือ ความกังวลมักเป็นงานเอกสารและความเชื่องช้า ถามว่าจะได้อย่างแรกโดยไม่ได้อย่างหลังได้อย่างไร เช่น รับคำศัพท์และแนวปฏิบัติไม่กี่อย่างมาใช้ และเลี่ยงแบบฟอร์ม บันทึกเงื่อนไขที่ทีมต้องการ

## ในทางปฏิบัติ: ตัวอย่าง ITIL แบบเอไจล์

ร้านค้าปลีกออนไลน์ขนาดกลางแห่งหนึ่งเติบโตจากเว็บไซต์ของผู้ก่อตั้งจนเป็นธุรกิจที่มีวิศวกรสิบสองคน ฐานลูกค้าที่เพิ่มขึ้น และเจ้าหน้าที่สนับสนุนกลุ่มเล็ก ลูกค้าส่งอีเมลแจ้งปัญหาไปยังกล่องจดหมายร่วม และโทรไปยังเบอร์มือถือส่วนตัวเมื่อขั้นตอนชำระเงินใช้ไม่ได้ วิศวกรแก้สิ่งที่ได้ยินและแทบไม่จดอะไรไว้ หลังระบบชำระเงินล่มนานสามชั่วโมง ผู้ก่อตั้งถามว่าเหตุใดจึงไม่มีใครรู้จนกระทั่งลูกค้าโทรมา

หัวหน้าฝ่ายวิศวกรรมเสนอ ITSM แบบเบาที่สุดเท่าที่จะเป็นไปได้ ทีมจดรายการบริการด้วยถ้อยคำของลูกค้า ได้แก่ เรียกดูและค้นหา ชำระเงิน ติดตามคำสั่งซื้อ และบัญชีลูกค้า แต่ละบริการมีเจ้าของ อีเมลสนับสนุนร่วมกลายเป็นประตูบานเดียว ป้อนเข้าเครื่องมือตั๋วแบบง่ายที่แยกประเภทเหตุการณ์ขัดข้องกับคำขอ เหตุการณ์ขัดข้องใดที่ยืดเยื้อเกิน 30 นาทีจะมีการทบทวนสั้นๆ เขียนไว้ในเอกสารร่วม การเปลี่ยนแปลงของระบบชำระเงินจะประกาศในช่องทางสนทนาของทีมก่อนลงมือทำ

หลังผ่านไปสามเดือน ทีมรู้ว่าตนจัดการเหตุการณ์ขัดข้องกี่เรื่อง และพบว่าส่วนใหญ่มาจากสองสาเหตุ ทีมแก้ทั้งสองอย่าง และการล่มของระบบชำระเงินก็ไม่เกิดซ้ำ ยังมีความยุ่งยากเหลืออยู่ ลูกค้ายังโทรหาผู้ก่อตั้งเมื่อไม่พอใจ ทำให้ความต้องการบางส่วนข้ามเครื่องมือตั๋วไป วิศวกรยังบ่นว่าการเขียนการทบทวนใช้เวลา และมีการทบทวนสองครั้งที่ถูกข้ามไปในเดือนที่งานยุ่ง หัวหน้าฝ่ายวิศวกรรมตัดสินใจให้การทบทวนสั้นไว้ ขอให้ผู้ก่อตั้งโอนสายไปยังที่อยู่สนับสนุน และกลับมาพิจารณาอีกครั้งหลังข้อมูลอีกหนึ่งไตรมาสว่าจำเป็นต้องมีกระบวนการแบบ ITIL ที่เต็มรูปแบบกว่านี้หรือไม่

## สี่มุมมอง

### ทีมผลิตภัณฑ์และทีมส่งมอบ

ทีมส่งมอบที่ดูแลสิ่งที่ตนสร้างก็ทำ ITSM อยู่แล้ว ตั้งชื่อบริการของคุณ บันทึกเหตุการณ์ขัดข้องและการเปลี่ยนแปลงแบบเบาๆ และแบ่งปันข้อมูลกับผู้ที่สนับสนุนบริการของคุณ มองศูนย์บริการเป็นแหล่งหลักฐานว่าผู้ใช้ติดขัดตรงไหน

### ทีมบริการและทีมปฏิบัติการ

เจ้าหน้าที่ปฏิบัติการและศูนย์บริการแบกแนวปฏิบัติ ITSM ส่วนใหญ่ แนวคิดเอไจล์ช่วยได้โดยทำให้งานของคุณมองเห็นได้ ทำให้วงจรป้อนกลับกับผู้ใช้สั้นลง และเปลี่ยนการปรับปรุงจากโครงการประจำปีเป็นการเปลี่ยนแปลงเล็กๆ สม่ำเสมอ อธิบายเจตนารมณ์เบื้องหลังกฎ ITSM แต่ละข้อ เพื่อให้เพื่อนร่วมงานปรับใช้ได้อย่างเหมาะสม

### ภาวะผู้นำและธรรมาภิบาล

ผู้นำตัดสินใจว่าจะกำหนดโครงสร้างมากเพียงใดและขอหลักฐานมากเพียงใด ขอผลลัพธ์ที่ลูกค้ารู้สึกได้ และตัวชี้วัดไม่กี่ตัวที่ทีมสร้างได้จากเครื่องมือของตน ระวังการซื้อกรอบแนวทางเพื่อเป็นสัญญาณ บทความ Wikipedia แจกแจงไว้หลายกรอบ และไม่มีกรอบใดทดแทนการรู้จักบริการของตนเองได้

### ลูกค้าและผู้ใช้

ลูกค้าและผู้ใช้คือเหตุผลที่ ITSM มีอยู่ พึงคาดหวังช่องทางขอความช่วยเหลือที่ชัดเจน ข้อมูลที่ตรงไปตรงมาว่าควรคาดหวังอะไร และผู้ที่เป็นเจ้าของแต่ละบริการ ในทางกลับกัน ให้ข้อมูลที่ทันเวลาและเฉพาะเจาะจงเมื่อมีสิ่งผิดพลาด เพื่อให้ผู้ให้บริการเรียนรู้จากเรื่องนั้นได้

## รูปแบบความล้มเหลวที่พบบ่อย

- **กระบวนการเพื่อตัวกระบวนการเอง** แบบฟอร์มและการอนุมัติเพิ่มพูนขึ้นโดยไม่มีใครจำได้ว่าทำไป เพื่ออะไร แก้ไขโดยผูกแต่ละแนวปฏิบัติกับวัตถุประสงค์ และลบข้อที่ไม่ตอบวัตถุประสงค์ใดแล้ว
- **ไม่มีประตูบานเดียว** ผู้ใช้ไปหาคนที่ตนรู้จัก และความต้องการมองไม่เห็น แก้ไขโดยเสนอช่องทางเดียวที่ใช้ง่าย และรวบรวมคำขอไม่เป็นทางการเข้าช่องทางนั้น
- **ปนเหตุการณ์ขัดข้อง คำขอ และปัญหา** รายงานชี้นำผิดและสาเหตุยังซ่อนอยู่ แก้ไขโดยใช้นิยามง่ายๆ และจัดประเภทตั๋วอย่างสม่ำเสมอ
- **อธิบายบริการด้วยเทคโนโลยี** ผู้ใช้หาสิ่งที่ต้องการไม่พบ และเจ้าของไม่ชัดเจน แก้ไขโดยอธิบายบริการด้วยถ้อยคำของลูกค้าและระบุเจ้าของแต่ละบริการ
- **รับกรอบแนวทางมาทั้งชุด** ทีมคัดลอกกรอบแนวทางขนาดใหญ่แล้วจมอยู่กับกระบวนการ แก้ไขโดยเริ่มจากปัญหาและเลือกเฉพาะส่วนที่ช่วยได้
- **เพิกเฉยต่อผู้ใช้** ผู้ให้บริการพูดคุยเฉพาะกับลูกค้าผู้จ่ายเงิน แก้ไขโดยรับฟังทั้งลูกค้าและผู้ใช้ และมองหาความขัดแย้ง
- **วัดกิจกรรม** จำนวนตั๋วและสายโทรศัพท์เข้ามาแทนหลักฐานคุณภาพบริการ แก้ไขโดยวัดความพร้อมใช้งาน เวลาที่ใช้กู้คืนบริการ และความพึงพอใจของผู้ใช้
- **มอง ITSM แยกจากการส่งมอบ** ทีมส่งมอบปล่อยงานแล้วปล่อยให้ฝ่ายปฏิบัติการรับมือ แก้ไขโดยเชื่อมสองฝ่ายผ่านบริการร่วม ข้อมูลร่วม และการทบทวนร่วม (ดูหัวข้อ 5.1 — การบริหารบริการแบบเอไจล์)

| มิติ | เริ่มต้น | พัฒนา | สร้างมาตรฐาน | บริหารจัดการ | ประสานกลมกลืน |
|---|---|---|---|---|---|

| การสนับสนุนและคำขอ | ขอความช่วยเหลือผ่านช่องทางไม่เป็นทางการ | บางทีมมีเครื่องมือตั๋วหรือกล่องจดหมายร่วม | ประตูบานเดียวพร้อมประเภทที่ชัดเจนสำหรับเหตุการณ์ขัดข้องและคำขอ | ติดตามและทบทวนความต้องการและเวลาที่ใช้แก้ไข | การสนับสนุนประสานกันข้ามทีมและผู้ส่งมอบด้วยข้อมูลร่วม |
| บันทึกและตัวชี้วัด | เก็บบันทึกน้อย | บางทีมบันทึกเหตุการณ์ขัดข้องและการเปลี่ยนแปลง | บันทึกสม่ำเสมอและแต่ละบันทึกมีวัตถุประสงค์ที่ระบุไว้ | ทบทวนตัวชี้วัดที่ลูกค้ามองเห็นเป็นประจำ | ตัวชี้วัดถูกแบ่งปันข้ามบริการและใช้กำหนดลำดับความสำคัญร่วมกัน |
| การปรับปรุง | การแก้ไขตามหลังวิกฤต | บางทีมทบทวนเหตุการณ์ขัดข้อง | การทบทวนข้อมูลเหตุการณ์ขัดข้องและคำขออย่างสม่ำเสมอนำไปสู่การเปลี่ยนแปลงที่วางแผนไว้ | งานปรับปรุงมีทรัพยากรและตรวจสอบผลลัพธ์ | การปรับปรุงเป็นเรื่องปกติข้ามทีมและร่วมกับลูกค้า |

## รายการตรวจสอบ

- [ ] เรามีรายการบริการของเราด้วยภาษาของลูกค้า
- [ ] แต่ละบริการมีเจ้าของที่ระบุชื่อ
- [ ] เรารู้ว่าใครคือลูกค้าและใครคือผู้ใช้ของแต่ละบริการ
- [ ] ผู้ใช้มีประตูบานเดียวที่ชัดเจนสำหรับขอความช่วยเหลือและยื่นคำขอ
- [ ] เหตุการณ์ขัดข้อง คำขอ และปัญหาถูกบันทึกเป็นสิ่งที่แตกต่างกัน
- [ ] บันทึกแต่ละชนิดมีวัตถุประสงค์ที่ระบุไว้ และช่องข้อมูลที่ไม่ได้ใช้ถูกลบออก
- [ ] เราวัดอย่างน้อยหนึ่งสิ่งที่ลูกค้ารู้สึก เช่น ความพร้อมใช้งานหรือเวลาที่ใช้กู้คืนบริการ
- [ ] เราทบทวนข้อมูลเหตุการณ์ขัดข้องและคำขออย่างสม่ำเสมอและลงมือทำตามข้อมูลนั้น
- [ ] เราบอกได้ว่าเราใช้แนวคิดใดจากกรอบแนวทาง และละแนวคิดใดไว้
- [ ] เราระบุงานประจำที่ทำให้เป็นอัตโนมัติได้อย่างปลอดภัยแล้ว

## พรอมต์ปัญญาประดิษฐ์

**วัตถุประสงค์: ร่างรายการบริการของคุณด้วยภาษาของลูกค้า**

```text
Help me describe the services my team provides in the words our users would use.

Who we are and what we run: [describe the team and its main systems in a few sentences].
Who uses what: [list user groups and what each group does with our systems].
What we currently call our services: [paste a list, or write "none"].

Produce a draft list of 5 to 10 services, each with a one-sentence description from the user's point of view, the customer or user groups, and a suggested owner role. Mark each item that is a guess. Do not invent systems I did not mention. Ask clarifying questions first if information is missing, and list what you are unsure of.
```

**วัตถุประสงค์: จัดประเภทตั๋วล่าสุดเป็นเหตุการณ์ขัดข้อง คำขอ และปัญหา**

```text
Here are [number] recent tickets or messages to our team: [paste short, anonymized descriptions, one per line].

Definitions to use: an incident is an unplanned disruption or potential disruption to a service; a service request is a routine request for something the service normally provides; a problem is the underlying cause of one or more incidents.

Classify each item as incident, request, or possible problem, with one sentence of reasoning that uses only what I wrote. List items you could not classify and the question I should ask to decide. At the end, tell me the share in each category from my list only. Do not invent details, and list what you are unsure of.
```

**วัตถุประสงค์: เลือกชุดแนวปฏิบัติ ITSM ชุดเล็กชุดแรกที่เหมาะกับสถานการณ์ของคุณ**

```text
Help me choose a first set of IT service management practices for a team in this situation.

Team size and type: [describe].
Our biggest pains (with a recent example for each): [list].
Existing tools and records: [list, or write "none"].
Rules we must follow (audit, security, contracts), with source text if you have it: [paste, or write "none known"].

From these practices: service desk, incident management, problem management, change enablement, service request management, service level management, service catalog management, knowledge management, continual improvement, propose the two or three to start with and say why, using only the information above. Say what you would leave for later. Mark assumptions, ask clarifying questions first, and list what you are unsure of.
```

**วัตถุประสงค์: เตรียมการสนทนาระหว่างทีมส่งมอบกับศูนย์บริการ**

```text
Plan a 45-minute conversation between a delivery team and the service desk about how new changes are handed over.

Delivery team: [describe]. Service desk: [describe].
Recent example of a handover that went badly: [describe factually].
What the service desk says it needs: [list, or write "unknown"].

Produce an agenda, five questions for each side, and a closing step that records one agreed change with an owner. Keep it free of any particular tool. Ask clarifying questions first if information is missing, mark assumptions, and list what you are unsure of.
```

## แหล่งอ้างอิงหลัก

- **IT service management** (Wikipedia): นิยามสั้นๆ พร้อมรายการกรอบแนวทางและมาตรฐานที่เกี่ยวข้อง เป็นประโยชน์ในฐานะแผนที่
- **ITIL** (Wikipedia): ประวัติและเวอร์ชันของกรอบแนวทาง ITSM ที่รู้จักกันดีที่สุด รวมถึงการเปลี่ยนมือความเป็นเจ้าของ
- **ISO/IEC 20000** (Wikipedia): ความเป็นมาของมาตรฐานสากลสำหรับระบบการบริหารบริการ
- **Enterprise service management** (Wikipedia): บทนำเรื่องการนำแนวคิด ITSM ไปใช้นอกเหนือจากไอที
