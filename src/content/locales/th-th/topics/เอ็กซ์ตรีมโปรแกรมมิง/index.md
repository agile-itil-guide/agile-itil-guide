# เอ็กซ์ตรีมโปรแกรมมิง

**เอ็กซ์ตรีมโปรแกรมมิง (Extreme Programming หรือ XP) คือวิธีการแบบเอไจล์ที่เจาะจงที่สุดเรื่องแนวปฏิบัติด้านวิศวกรรม และนิสัยของมันในการทดสอบก่อน รวมระบบอย่างต่อเนื่อง และแบ่งปันความเป็นเจ้าของโค้ด คือสิ่งที่ทำให้การเปลี่ยนแปลงบ่อยกับบริการที่ใช้งานจริงปลอดภัย**

## เหตุใดเรื่องนี้จึงสำคัญ

การเปลี่ยนแปลงบ่อยคือเป้าหมายของการส่งมอบอย่างต่อเนื่องและเป็นความกังวลของการบริหารบริการ วิธีประสานสองสิ่งนี้ไม่ใช่การประชุมอนุมัติที่มากขึ้น แต่คือความสามารถที่แข็งแรงขึ้นในการรู้ว่าการเปลี่ยนแปลงใช้ได้ก่อนถึงผู้ใช้ เอ็กซ์ตรีมโปรแกรมมิงเป็นวิธีการแบบเอไจล์ที่พูดถึงการสร้างความสามารถนั้นมากที่สุด คือ เขียนการทดสอบก่อน รวมระบบวันละหลายครั้ง รักษาการออกแบบให้เรียบง่าย และแบ่งปันความรับผิดชอบต่อโค้ด

ทีมจำนวนมากรับเหตุการณ์และกระดานของ Scrum แต่ทิ้งแนวปฏิบัติด้านวิศวกรรมไว้ข้างหลัง ผลคือทีมที่วางแผนเป็นสปรินต์แต่ปล่อยด้วยความกลัว แนวปฏิบัติของ XP คือครึ่งที่หายไป สิ่งเหล่านี้สำคัญต่อทุกคนที่ต้องดำเนินผลลัพธ์ เพราะบริการที่สร้างด้วยการทดสอบอัตโนมัติ การปล่อยเล็ก และความรู้ที่แบ่งปัน สนับสนุนได้ง่ายกว่าบริการที่สร้างโดยคนไม่กี่คนเป็นชุดใหญ่ที่ไม่ผ่านการทดสอบ

XP ยังขอบางอย่างจากองค์กรที่มองข้ามได้ง่าย คือจังหวะที่ยั่งยืน ทีมครบวงจรที่มีทักษะทั้งหมดที่ต้องการ และลูกค้าที่พร้อมให้ติดต่อจริง ๆ สิ่งเหล่านี้เป็นเงื่อนไขของสภาพแวดล้อมการทำงาน ไม่ใช่แค่นิสัยของโปรแกรมเมอร์ หัวข้อนี้อธิบายวิธีการ หลักฐานเกี่ยวกับข้อจำกัดของมัน และวิธีที่แนวปฏิบัติของมันเชื่อมกับแนวปฏิบัติของ ITIL เช่น การสนับสนุนการเปลี่ยนแปลง การบริหารการปล่อย และการบริหารความรู้

## แนวคิดหลัก

### XP มาจากไหน

Kent Beck พัฒนา XP ขณะทำงานในระบบ Chrysler Comprehensive Compensation System (C3) ซึ่งเป็นโครงการเงินเดือน ตาม[บทความ Wikipedia เรื่อง Extreme programming](https://en.wikipedia.org/wiki/Extreme_programming) Beck เป็นหัวหน้าโครงการในเดือนมีนาคม 1996 และปรับปรุงวิธีการที่นั่น โดย Ward Cunningham เป็นผู้มีอิทธิพลสำคัญ และ Ron Jeffries เข้ามาเป็นโค้ชทีม หนังสือ *Extreme Programming Explained* ของเขาปรากฏในเดือนตุลาคม 1999 Chrysler ยกเลิกโครงการ C3 ในเดือนกุมภาพันธ์ 2000 หลัง Daimler-Benz เข้าซื้อบริษัท

บทความชี้ว่าแนวปฏิบัติ XP จำนวนมากไม่ใช่ของใหม่ โดยกล่าวถึงการพัฒนาแบบทดสอบก่อนในโครงการ Mercury ของ NASA ในต้นทศวรรษ 1960 ท่าของ XP คือการนำแนวปฏิบัติที่ดีไปสู่ระดับ "สุดขั้ว" ถ้าการทดสอบดี ก็ทดสอบตลอดเวลา ถ้าการทบทวนดี ก็ทบทวนอยู่เสมอด้วยการทำงานเป็นคู่ Beck และ Cunningham เป็นหนึ่งใน 17 คนที่เขียนแถลงการณ์เอไจล์ (ดู หัวข้อ 1.1 — แถลงการณ์เอไจล์)

### คุณค่าห้าข้อ

XP ระบุคุณค่าห้าข้อ

| คุณค่า | ความหมาย | ในงานบริการ |
|---|---|---|
| **การสื่อสาร (Communication)** | สร้างความเข้าใจร่วมกันระหว่างนักพัฒนา ผู้ใช้ และลูกค้า โดยหลักคือการพูดคุยและรักษาการออกแบบให้เรียบง่าย | นักพัฒนาและบุคลากรฝ่ายปฏิบัติการพูดคุยกันว่าการปล่อยจะทำงานอย่างไรก่อนส่งมอบ |
| **ความเรียบง่าย (Simplicity)** | ทำสิ่งที่เรียบง่ายที่สุดที่ใช้ได้ และไม่สร้างเพื่อความต้องการในอนาคตที่เป็นการคาดเดา | มีชิ้นส่วนเคลื่อนไหวน้อยลงให้เฝ้าติดตาม รักษาความมั่นคงปลอดภัย และอธิบาย |
| **ข้อเสนอแนะ (Feedback)** | เรียนรู้อย่างรวดเร็วจากการทดสอบ จากลูกค้า และจากการประมาณของทีมเอง | ผลการทดสอบที่เร็วและการเฝ้าติดตามการผลิตย่นเวลาในการเรียนรู้ |
| **ความกล้า (Courage)** | ปรับโครงสร้างโค้ด ทิ้งโค้ดที่ล้าสมัย และยืนหยัดผ่านปัญหายาก | เลิกใช้องค์ประกอบเก่าที่ไม่มีใครกล้าแตะ |
| **ความเคารพ (Respect)** | เคารพเพื่อนร่วมทีมและงานของตนเอง | การทบทวนโดยไม่กล่าวโทษหลังความล้มเหลว และภาระเวรสแตนด์บายที่เป็นธรรม |

บทความระบุว่าความเคารพถูกเพิ่มในหนังสือ *Extreme Programming Explained* ฉบับที่สอง ต่อจากสี่ข้อเดิม

### แนวปฏิบัติ

บทความเรื่องแนวปฏิบัติ XP จัดกลุ่มแนวปฏิบัติสิบสองข้อเป็นสี่ชุด เข้าใจได้ดีที่สุดเมื่อมองเป็นระบบที่ค้ำจุนตนเอง

| กลุ่ม | แนวปฏิบัติ | วัตถุประสงค์ |
|---|---|---|
| **ข้อเสนอแนะระดับละเอียด** | การเขียนโปรแกรมเป็นคู่ เกมการวางแผน (planning game) การพัฒนาโดยใช้การทดสอบนำ ทีมทั้งหมด (whole team) | ได้ข้อเสนอแนะในไม่กี่นาทีหรือไม่กี่วัน ไม่ใช่หลายเดือน |
| **กระบวนการต่อเนื่อง** | การรวมระบบอย่างต่อเนื่อง การปรับปรุงการออกแบบ (refactoring) การปล่อยเล็ก | รักษาซอฟต์แวร์ให้อยู่ในสถานะที่ปล่อยได้เสมอ |
| **ความเข้าใจร่วมกัน** | มาตรฐานการเขียนโค้ด ความเป็นเจ้าของโค้ดร่วมกัน การออกแบบเรียบง่าย อุปมาของระบบ (system metaphor) | ให้ใครในทีมก็เปลี่ยนส่วนใดส่วนหนึ่งได้อย่างปลอดภัย |
| **สวัสดิภาพของโปรแกรมเมอร์** | จังหวะที่ยั่งยืน | ให้ผู้คนได้พักและมีประสิทธิผลตลอดหลายปี |

คำอธิบายสั้น ๆ ของแนวปฏิบัติหลัก

- **การเขียนโปรแกรมเป็นคู่ (Pair programming):** คนสองคนทำงานเดียวกันที่เครื่องเดียว คนหนึ่งเขียนและอีกคนทบทวน และสลับคู่บ่อย
- **การพัฒนาโดยใช้การทดสอบนำ (TDD):** โปรแกรมเมอร์เขียนการทดสอบที่ล้มเหลวก่อน แล้วเขียนโค้ดเท่าที่จำเป็นให้ผ่าน
- **การรวมระบบอย่างต่อเนื่อง (CI):** นักพัฒนารวมงานเข้าที่เก็บร่วมทุกไม่กี่ชั่วโมง เพื่อให้ปัญหาการรวมปรากฏแต่เนิ่น ๆ
- **การปล่อยเล็ก (Small releases):** ส่งมอบซอฟต์แวร์ที่ใช้งานได้เป็นก้าวเล็กบ่อย ๆ เพื่อให้ลูกค้าเห็นความก้าวหน้าและตอบสนอง
- **ความเป็นเจ้าของโค้ดร่วมกัน (Collective code ownership):** ใครในทีมก็เปลี่ยนส่วนใดของโค้ดก็ได้
- **จังหวะที่ยั่งยืน (Sustainable pace):** หลีกเลี่ยงการทำงานล่วงเวลาเป็นประจำ และไม่อนุญาตให้ทำงานล่วงเวลาสองสัปดาห์ติดกัน

### ข้อถกเถียงและข้อจำกัด

บทความบันทึกข้อวิจารณ์หลายข้อ Matt Stephens และ Doug Rosenberg ในหนังสือปี 2003 ให้เหตุผลว่าแนวปฏิบัติของ XP พึ่งพากัน ดังนั้นการรับเพียงบางส่วนบ่อนทำลายกระบวนการ นักวิจารณ์ยังตั้งคำถามกับการเขียนโปรแกรมเป็นคู่ในฐานะวิธีทำงานปกติ การไม่มีการออกแบบใหญ่ล่วงหน้า ลูกค้าประจำสถานที่ในฐานะจุดล้มเหลวเดี่ยว และคำขอเปลี่ยนแปลงที่ไม่เป็นทางการที่นำไปสู่การทำใหม่และขอบเขตที่ขยายเกินควบคุม P. McBreen และ Boehm กับ Turner ก็เขียนการประเมินเชิงวิพากษ์เช่นกัน บทความเสริมว่าผู้ปฏิบัติงานเอไจล์มองข้อวิจารณ์เหล่านี้จำนวนมากเป็นความเข้าใจผิด

เรื่องการขยาย บทความระบุว่า Industrial XP ซึ่งเริ่มในปี 2004 ขยาย XP ไปสู่ทีมที่ใหญ่ขึ้นและกระจาย ด้วยแนวปฏิบัติ 23 ข้อ บทความยังรายงานข้ออ้างที่ระบุว่าต้องการการอ้างอิงว่า ThoughtWorks ประสบความสำเร็จพอสมควรในโครงการ XP แบบกระจายที่มีคนถึงหกสิบคน อ่านข้ออ้างนั้นด้วยความระมัดระวัง และดู หัวข้อ 1.8 — การขยายเอไจล์ สำหรับการอภิปรายที่กว้างกว่า

บทความไม่ได้พูดถึงการติดตั้งหรือการเฝ้าติดตามการผลิตนอกเหนือจากการรวมระบบอย่างต่อเนื่องและการปล่อยเล็ก XP พูดน้อยมากเรื่องการดำเนินซอฟต์แวร์ คุณนำสิ่งนั้นมาจากการบริหารบริการ และใช้ XP เพื่อทำให้การส่งมอบงานเสี่ยงน้อยลง

### XP กับมุมมองของ ITIL ต่อการเปลี่ยนแปลง

แนวปฏิบัติการสนับสนุนการเปลี่ยนแปลงของ ITIL (ดู หัวข้อ 3.4 — การสนับสนุนการเปลี่ยนแปลง) เกี่ยวข้องกับการทำให้แน่ใจว่าการเปลี่ยนแปลงได้รับการประเมิน อนุมัติ และกำหนดเวลา เพื่อควบคุมความเสี่ยง XP ควบคุมความเสี่ยงในที่อื่น คือในโค้ด ผ่านการทดสอบ ก้าวเล็ก และความรู้ที่แบ่งปัน การเปลี่ยนแปลงที่เล็ก ทดสอบอัตโนมัติ รวมระบบแล้ว และย้อนกลับได้ง่ายเป็นการเปลี่ยนแปลงที่ความเสี่ยงต่ำกว่าตามการประเมินที่สมเหตุสมผลใด ๆ ทั้งสองมุมมองเข้ากันได้เมื่อหลักฐานจากแนวปฏิบัติของ XP ถูกใช้ในการตัดสินใจเรื่องการเปลี่ยนแปลง

## แนวปฏิบัติที่ดี

1. **รับแนวปฏิบัติเป็นชุด** ข้อสังเกตของนักวิจารณ์ว่าแนวปฏิบัติของ XP ค้ำจุนกันเป็นคำเตือนที่มีประโยชน์ การทดสอบโดยไม่มีการรวมระบบ หรือการรวมระบบโดยไม่มีก้าวเล็ก ให้ผลน้อยกว่าผลรวม แนะนำไปพร้อมกันเมื่อทำได้ และเรียนรู้ว่าแนวปฏิบัติใดที่อันอื่นพึ่งพา
2. **เขียนการทดสอบก่อนสำหรับการเปลี่ยนแปลงที่สำคัญ** สำหรับพฤติกรรมใหม่หรือการแก้บั๊ก เขียนการทดสอบที่ล้มเหลวซึ่งแสดงปัญหา แล้วจึงแก้ การทดสอบคงอยู่เป็นเครื่องป้องกันไม่ให้ปัญหากลับมา ซึ่งมีประโยชน์เป็นพิเศษสำหรับข้อบกพร่องที่ทำให้เกิดเหตุการณ์ขัดข้อง
3. **รวมระบบวันละหลายครั้ง** ให้สาขามีอายุสั้น และสร้างกับทดสอบโดยอัตโนมัติทุกการรวม การที่การสร้างเสียคือลำดับแรกของทีม
4. **ปล่อยเป็นก้าวเล็ก** การปล่อยเล็กแต่ละครั้งมีความเสี่ยงน้อยกว่าและเข้าใจกับย้อนกลับได้ง่ายกว่า มุ่งสู่ช่วงห่างที่สั้นที่สุดที่สายพานของคุณรองรับได้อย่างปลอดภัย และย่นให้สั้นลงเมื่อความมั่นใจเพิ่ม
5. **ปรับโครงสร้างโค้ดอย่างต่อเนื่อง** ปรับปรุงการออกแบบเล็กน้อยทุกวันแทนการเก็บไว้เขียนใหม่ทั้งหมด ชุดทดสอบคือสิ่งที่ทำให้สิ่งนี้ปลอดภัย
6. **รักษาการออกแบบให้เรียบง่ายที่สุดเท่าที่ทำได้** สร้างสิ่งที่จำเป็นตอนนี้ และลบสิ่งที่ไม่ได้ใช้ ระบบที่เล็กกว่ามีสิ่งให้เฝ้าติดตาม แพตช์ และอธิบายน้อยกว่า
7. **แบ่งปันความเป็นเจ้าของโค้ด** ให้สมาชิกทีมคนใดก็เปลี่ยนส่วนใดก็ได้ โดยมีการทดสอบและมาตรฐานร่วมสนับสนุน วิธีนี้ลดการพึ่งพาผู้เชี่ยวชาญไม่กี่คน ซึ่งก็เป็นความเสี่ยงด้านความพร้อมใช้งานของบริการด้วย
8. **จับคู่ในงานเสี่ยงหรือไม่คุ้นเคย** ใช้การจับคู่สำหรับการเปลี่ยนแปลงที่ยุ่งยาก การปฐมนิเทศ และการเงาตามเวรสแตนด์บาย มองเป็นเครื่องมือกระจายความรู้และจับข้อผิดพลาด และอย่าทำให้เป็นกฎสำหรับทุกงาน
9. **รักษาจังหวะที่ยั่งยืน** วางแผนงานให้การทำงานล่วงเวลาเกิดน้อยและไม่ซ้ำสัปดาห์แล้วสัปดาห์เล่า วิศวกรเวรสแตนด์บายที่เหนื่อยล้าเป็นความเสี่ยงต่อบริการ (ดู หัวข้อ 1.2 — หลักการเอไจล์ เรื่องจังหวะ)
10. **ทำให้ลูกค้าเป็นส่วนหนึ่งของทีม** หาผู้ใช้จริงหรือตัวแทนผู้ใช้ที่ตอบคำถามได้ระหว่างทำงาน จำข้อวิจารณ์ที่ว่าคนเดียวเป็นจุดล้มเหลวเดี่ยว จึงควรให้มีเสียงมากกว่าหนึ่งเสียง
11. **เขียนเกณฑ์การยอมรับเป็นการทดสอบเมื่อทำได้** เปลี่ยนความคาดหวังของลูกค้าเป็นการตรวจอัตโนมัติที่รันทุกการสร้าง วิธีนี้ทั้งบันทึกพฤติกรรมและปกป้องมันในเวลาเดียวกัน
12. **รวมการตรวจด้านปฏิบัติการในการทดสอบ** เพิ่มการตรวจการเฝ้าติดตาม การบันทึกล็อก และพฤติกรรมการกู้คืนในสายพาน เพื่อให้ความพร้อมด้านปฏิบัติการถูกตรวจสอบกับทุกการเปลี่ยนแปลง (ดู หัวข้อ 3.5 — การบริหารการปล่อยและการติดตั้ง)

## คำถามสำหรับพูดคุยกับทีมของคุณ

**เรารู้ได้อย่างไรว่าการเปลี่ยนแปลงใช้ได้ก่อนถึงผู้ใช้ และใช้เวลานานเท่าใดจึงรู้**

ติดตามการตรวจที่การเปลี่ยนแปลงผ่านระหว่างแล็ปท็อปของนักพัฒนากับการผลิต นับว่ากี่อย่างเป็นอัตโนมัติและแต่ละอย่างใช้เวลานานเท่าใด คำตอบทั่วไปรวมถึงการทดสอบด้วยมือ การทบทวน และความหวัง ถามว่าการตรวจใดจับปัญหาได้มากที่สุดและการตรวจใดไม่เคยจับอะไรเลย ต่อด้วยการเลือกการตรวจด้วยมือหนึ่งอย่างเพื่อทำให้เป็นอัตโนมัติ

**ใครเปลี่ยนส่วนใดของระบบเราได้ และเกิดอะไรขึ้นเมื่อคนเหล่านั้นไม่อยู่**

ลงรายการองค์ประกอบและผู้ที่เข้าใจแต่ละส่วน องค์ประกอบที่มีคนเดียวอยู่เบื้องหลังเป็นความเสี่ยงต่อบริการ ความเป็นเจ้าของร่วมกันคือคำตอบของ XP และต้องมีการทดสอบและมาตรฐานร่วมจึงจะปลอดภัย ถามว่าคนหนึ่งสอนอีกคนได้อะไรในหนึ่งเดือน ผู้อำนวยความสะดวกถามได้ว่าวันหยุดหรือการเจ็บป่วยเคยทำให้การแก้ไขล่าช้าหรือไม่

**การจับคู่จะช่วยเราที่สุดตรงไหน และตรงไหนที่มันแค่ทำให้เราช้าลง**

การเขียนโปรแกรมเป็นคู่เป็นที่ถกเถียง จึงเชิญให้ออกความเห็นอย่างซื่อสัตย์ ถามผู้คนเกี่ยวกับการจับคู่ที่ดีที่สุดและแย่ที่สุดที่เคยทำ การจับคู่มักช่วยกับระบบที่ไม่คุ้นเคย การเปลี่ยนแปลงที่ยุ่งยาก และการปฐมนิเทศ ช่วยน้อยกว่ากับงานประจำที่คนเดียวทำได้ดี ตกลงสถานการณ์หนึ่งเพื่อลองจับคู่หนึ่งเดือน และวิธีที่จะตัดสิน

**คุณภาพของเราเป็นอย่างไรเมื่ออยู่ใต้แรงกดดัน และเราทิ้งอะไรก่อน**

ขอตัวอย่างช่วงเร่งงานล่าสุดและสิ่งที่ถูกข้าม เช่น การทดสอบ การทบทวน เอกสาร ถามว่าเกิดอะไรขึ้นหลังจากนั้น มักพบว่างานที่ข้ามกลับมาเป็นเหตุการณ์ขัดข้อง ประเด็นคือสังเกตรูปแบบและตัดสินล่วงหน้าว่าแนวปฏิบัติใดได้รับการปกป้อง หลีกเลี่ยงการโทษ และเชื่อมคำตอบกับจังหวะที่ยั่งยืน

**เรารวมงานของเราบ่อยแค่ไหน และอะไรทำให้เราต้องรอ**

ถามว่าสาขาทั่วไปมีอายุนานเท่าใดและอะไรหน่วงมัน สาขาที่ยาวมักสะท้อนการเปลี่ยนแปลงใหญ่ การทบทวนที่ช้า หรือการสร้างที่ไม่น่าเชื่อถือ แต่ละอย่างแก้ต่างกัน ถามว่าทีมทำอะไรได้เพื่อให้การรวมภายในไม่กี่ชั่วโมงเป็นเรื่องปกติ เลือกอุปสรรคหนึ่งอย่างเพื่อขจัด

**เรามีลูกค้าหรือผู้ใช้ที่ทีมติดต่อได้หรือไม่ หรือเรากำลังเดาว่าพวกเขาต้องการอะไร**

ถามว่าใครตอบคำถามเกี่ยวกับความต้องการของผู้ใช้ และใช้เวลานานเท่าใด หากคำตอบเป็นสายโซ่ยาว ถามว่าคำถามใดที่ทำให้ผิดพลาดแล้วเสียต้นทุนมากที่สุด จำนักวิจารณ์ของ XP เอง ตัวแทนลูกค้าคนเดียวเป็นคอขวดได้ พูดคุยวิธีเข้าถึงผู้ใช้หลายคนอย่างสั้นและบ่อย

## ในทางปฏิบัติ: ตัวอย่าง ITIL แบบเอไจล์

ทีมดิจิทัล 9 คนของหน่วยงานขนส่งสาธารณะสร้างและดำเนินแอปวางแผนการเดินทางและฟีดข้อมูลเวลาถึงแบบสดที่นักพัฒนาอื่นในเมืองใช้ ทีมปล่อยรายเดือนหลังรอบการทดสอบด้วยมือสี่วัน เมื่อการปล่อยผิดพลาด การย้อนกลับใช้เวลาครึ่งวัน ทีมจึงลังเลที่จะปล่อยบ่อยขึ้น หัวหน้าฝ่ายปฏิบัติการ ซึ่งเป็นนักพัฒนาที่มีประสบการณ์มากที่สุดด้วย รับสายนอกเวลาส่วนใหญ่ เพราะไม่มีคนอื่นรู้ว่าฟีดทำงานอย่างไร

ทีมตัดสินใจรับแนวปฏิบัติ XP ไม่กี่อย่างไปพร้อมกัน ตั้งค่าการรวมระบบอย่างต่อเนื่องที่สร้างและรันการทดสอบหน่วยทุกการรวม สำหรับทุกบั๊กที่พบในการผลิต เขียนการทดสอบที่ล้มเหลวก่อนแก้ นักพัฒนาสองคนจับคู่กับหัวหน้าฝ่ายปฏิบัติการในงานฟีดวันละหนึ่งชั่วโมง ทีมยังเพิ่มขั้นตอนการติดตั้งที่สลับกลับไปเวอร์ชันก่อนหน้าได้ในไม่กี่นาที

หลังสี่เดือน ทีมปล่อยทุกสัปดาห์ ชุดทดสอบจับการถดถอยสองรายการก่อนปล่อย ซึ่งรอบด้วยมือจะพบเฉพาะวันสุดท้าย นักพัฒนาสามคนจัดการสายฟีดส่วนใหญ่ได้แล้ว ไม่ใช่ทุกอย่างได้ผล ชุดทดสอบใช้เวลารัน 25 นาที นักพัฒนาจึงรวมน้อยกว่าที่ตั้งใจ และการเปลี่ยนแปลงที่ผิดพลาดของฟีดเวลาถึงหลุดไปเพราะการทดสอบใช้ข้อมูลตัวอย่างที่ไม่ตรงกับกรณีขอบจริง ทีมย้ายการทดสอบที่ช้าไปขั้นที่สองเพื่อให้ผลแรกมาภายในห้านาที และเพิ่มการตรวจเฝ้าติดตามผลลัพธ์ของฟีด พวกเขายังตกลงว่าการจับคู่จะคงเป็นเครื่องมือสำหรับปัญหายากและการปฐมนิเทศ ไม่ใช่กฎสำหรับทุกงาน

## สี่มุมมอง

### ทีมผลิตภัณฑ์และทีมส่งมอบ

ทีมส่งมอบเป็นเจ้าของแนวปฏิบัติของ XP เริ่มจากสิ่งที่ให้ข้อเสนอแนะเร็วที่สุด คือการทดสอบอัตโนมัติและการรวมระบบอย่างต่อเนื่อง ปฏิบัติต่อชุดทดสอบของคุณเป็นผลิตภัณฑ์ที่ฝ่ายปฏิบัติการใช้ด้วย มันบอกว่าบริการควรทำอะไร และบอกอย่างรวดเร็วเมื่อมันเลิกทำ

### ทีมบริการและทีมปฏิบัติการ

บุคลากรฝ่ายปฏิบัติการใช้แนวคิดของ XP กับงานของตนได้ เช่น การเปลี่ยนแปลงโครงสร้างพื้นฐานและคอนฟิกูเรชันที่ทดสอบก่อนรัน การเปลี่ยนแปลงเล็กที่รวมบ่อย และความรู้ที่แบ่งปันทั่วทีมผ่านการจับคู่และความเป็นเจ้าของร่วม ขอให้ทีมส่งมอบเขียนการทดสอบที่ครอบคลุมความล้มเหลวที่คุณเห็นในการผลิต และเสนอประวัติเหตุการณ์ขัดข้องเพื่อนำทางว่าจะทดสอบอะไร

### ภาวะผู้นำและธรรมาภิบาล

ผู้นำเอื้อให้ XP เกิดผลโดยปกป้องจังหวะ จ่ายค่าโครงสร้างพื้นฐานการสร้างและทดสอบ และยอมรับว่าคุณภาพถูกสร้างเข้าไปในงาน ไม่ใช่ตรวจสอบเอาทีหลัง ขอหลักฐานความปลอดภัยที่มาจากสายพาน เช่น ผลการทดสอบและประวัติการปล่อย และอย่าเรียกร้องหลักฐานด้วยมือซ้ำซ้อน

### ลูกค้าและผู้ใช้

ลูกค้ามีบทบาทตรงที่สุดใน XP คือเป็นส่วนหนึ่งของวงจรข้อเสนอแนะของทีม คาดว่าจะถูกขอให้ลองการปล่อยเล็ก ตอบคำถามเร็ว และบอกว่าอะไรสำคัญที่สุดในสัปดาห์นี้ ในทางกลับกัน คุณควรเห็นเรื่องน่าประหลาดใจน้อยลงและการแก้ปัญหาที่คุณรายงานเร็วขึ้น

## รูปแบบความล้มเหลวที่พบบ่อย

- **รับเฉพาะพิธีกรรม** ทีมรับการประชุมยืนและกระดานแต่ข้ามการทดสอบและการรวมระบบ แต่ควรเริ่มด้วยการทดสอบอัตโนมัติและการรวมระบบอย่างต่อเนื่อง เพราะให้ผลตอบแทนมากที่สุด
- **มองการจับคู่เป็นกฎ** การบังคับจับคู่กับทุกงานทำให้ผู้คนคับข้องใจและงานประจำช้าลง แต่ควรใช้การจับคู่กับปัญหายาก การปฐมนิเทศ และการถ่ายโอนความรู้ และทบทวนว่าได้ผลอย่างไร
- **ชุดทดสอบที่ไม่มีใครไว้ใจ** การทดสอบที่ช้าหรือไม่น่าเชื่อถือถูกเพิกเฉย แต่ควรรักษาชุดให้เร็วและแก้หรือลบการทดสอบที่ไม่เสถียร (flaky) โดยเร็ว
- **ความเป็นเจ้าของร่วมโดยไม่มีมาตรฐาน** ใครก็เปลี่ยนอะไรก็ได้ และโค้ดเสื่อมสภาพ แต่ควรจับคู่กับมาตรฐานการเขียนโค้ดร่วม การทบทวน และการตรวจอัตโนมัติ
- **ตัวแทนลูกค้าคนเดียว** คนเดียวกลายเป็นคอขวดหรือแหล่งของอคติ แต่ควรกระจายการติดต่อไปยังผู้ใช้หลายคนและตรวจการตัดสินใจกับการใช้งานจริง
- **ข้ามการออกแบบโดยสิ้นเชิง** ทีมปรับโครงสร้างซ้ำ ๆ โดยไม่มีทิศทาง แต่ควรเก็บภาพเบา ๆ ของสถาปัตยกรรมและทบทวนเป็นระยะ
- **การทำงานล่วงเวลาเป็นเรื่องปกติ** ชั่วโมงยาวกัดกร่อนคุณภาพและก่อเหตุการณ์ขัดข้อง แต่ควรวางแผนตามจังหวะที่ยั่งยืนและมองการทำงานล่วงเวลาซ้ำ ๆ เป็นสัญญาณให้ลดขอบเขต
- **เพิกเฉยต่อฝ่ายปฏิบัติการ** XP พูดน้อยเรื่องการดำเนินซอฟต์แวร์ และทีมสันนิษฐานว่าครอบคลุมแล้ว แต่ควรเพิ่มการตรวจด้านปฏิบัติการในการทดสอบและเชิญบุคลากรฝ่ายปฏิบัติการเข้าร่วมการวางแผน

## พรอมต์ปัญญาประดิษฐ์

**วัตถุประสงค์: เปลี่ยนเหตุการณ์ขัดข้องในการผลิตเป็นการทดสอบและรายการบทเรียน**

```text
Help me learn from a production incident using Extreme Programming habits.

Incident description (factual, blameless, in order): [paste what happened, how it was detected, and how it was fixed].
The part of the system involved: [describe the component and what it does].
Our current tests for that part: [describe what is tested today, or write "unknown"].

Propose: (1) a test, described in plain words, that would have caught this before release; (2) two other tests worth adding nearby; (3) one change to our release process to make a similar fault less likely. Do not invent details about our system. Ask clarifying questions first if the description is too thin, mark assumptions, and list what you are unsure of.
```

**วัตถุประสงค์: ประเมินว่าทีมของคุณปล่อยการเปลี่ยนแปลงเล็กได้ปลอดภัยเพียงใด**

```text
I want to understand how safe it is for our team to release small changes often.

Our path from change to production, step by step: [paste the steps, who does each, and roughly how long each takes].
Our automated checks: [list tests, builds, and scans, or write "none"].
How we roll back: [describe].
The last two releases that went wrong: [paste short factual descriptions].

Identify the steps that rely on manual work or one person's knowledge. For each, suggest one small automation or sharing step. Do not claim any standard requires something unless I pasted its text. Separate what the text shows from what you assume, and list what you are unsure of.
```

**วัตถุประสงค์: ออกแบบการทดลองการจับคู่หนึ่งเดือน**

```text
Help me design a one-month experiment with pair programming for a team of [number] people working on [type of system].

Our reasons for trying it: [for example "reduce single points of failure on the feed service"].
Constraints: [for example remote working, on-call duties, mixed experience levels].

Propose which kinds of work to pair on and which to leave alone, how to rotate partners, what to observe (use observations such as questions answered and defects found, and do not invent numbers), and how the team will decide at the end whether to continue. Ask clarifying questions first, mark assumptions, and list what you are unsure of.
```

**วัตถุประสงค์: ตรวจสอบนิยามของเสร็จเพื่อความพร้อมด้านปฏิบัติการ**

```text
Here is our current Definition of Done: [paste it].
Things the operations or support team has asked for: [paste, or write "unknown"].

Compare the two. List items operations would need that are missing, and for each one say whether it could be checked automatically in a build pipeline, and how. Do not state that any standard requires an item unless I have pasted its text. Mark assumptions and list what you are unsure of.
```

## ทักษะปัญญาประดิษฐ์

- [extreme-programming](../../../../skills/extreme-programming/SKILL.md): ใช้เพื่อทบทวนหรือแนะนำแนวปฏิบัติ XP เช่น การจับคู่ การพัฒนาโดยใช้การทดสอบนำ และการรวมระบบอย่างต่อเนื่อง
- [user-story](../../../../skills/user-story/SKILL.md): ใช้เพื่อเปลี่ยนความต้องการของลูกค้าเป็นเรื่องราวพร้อมเกณฑ์การยอมรับที่กลายเป็นการทดสอบอัตโนมัติได้
- [agile-delivery](../../../../skills/agile-delivery/SKILL.md): ใช้เพื่อวางแผนการปล่อยเล็กบ่อยและการตรวจที่ทำให้ปลอดภัย
- [agile-reflection](../../../../skills/agile-reflection/SKILL.md): ใช้เพื่อทบทวนว่าแนวปฏิบัติทำงานได้ดีเพียงใดและเลือกการเปลี่ยนแปลงหนึ่งอย่าง
- [runbook](../../../../skills/runbook/SKILL.md): ใช้เพื่อเปลี่ยนความรู้ที่คนเดียวถือไว้ให้เป็นขั้นตอนที่แบ่งปันและทดสอบแล้ว

## แหล่งอ้างอิงหลัก

- **Extreme programming** และ **Extreme programming practices** (Wikipedia): ภาพรวมของประวัติ คุณค่า แนวปฏิบัติ และข้อวิจารณ์ พร้อมการอ้างอิง

- **Extreme Programming Refactored: The Case Against XP** (Matt Stephens และ Doug Rosenberg, 2003): ข้อวิจารณ์ที่รู้จักกันดีที่สุด มีประโยชน์สำหรับทดสอบข้อสันนิษฐานของคุณเอง
